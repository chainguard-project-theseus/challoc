# challoc step-back review, 2026-09-18

A pre-release review of the code, the design document and the security
claims, written after Phase 1.5 ended BLOCKED at commit `6a9016e` (code at
`2c8731f`). The previous review (`docs/review-2026-09-17.md`) asked where
the cycles go; this one asks whether the code we have is the code we want
to ship, and what the shortest path from here to the goal is. Nothing was
implemented in this session. The measurements it relies on are the ones
already in `bench/results/` and the two scorecards; the only things run for
it were correctness checks in the Mac dev container (section 1.1), whose
numbers are never compared with GCE numbers. Both reference VMs stayed
stopped.

Method: the docs (README, design, plan, the previous review, all 302
entries of PROGRESS.md's decision record, the acceptance files and the
scorecards) were read in full; the source was read module by module by
six parallel reviewers with distinct briefs (security claims; the
heap/class/arena seams; huge/purge/meta/layout/sys/config; design versus
code; the previous review's calibration; API surface and shipping
artifacts) plus one dedicated to the `calloc` failure of section 1.1.
Every finding below that says "verified" was confirmed against the code by
a second reading; "suspected" means the reading is consistent but was not
executed.

## 0. Summary

**The allocator works and is fast where it matters, but it is not
releasable as it stands, for reasons that have nothing to do with the
benchmark row the phase is blocked on.**

1. **One correctness failure was observed** (section 1.1): in this
   session's `make test`, mimalloc's stress test aborted because `calloc`
   returned memory containing a non-zero word. It did not reproduce in 150
   standalone and parallel reruns, so it is a race. Whatever the mechanism,
   `calloc` handing out dirty memory (or one slot to two threads) is a
   memory-safety failure of the kind the project exists to prevent, and it
   must be root-caused before anything else is scheduled. The reading
   that hunted it excluded every interleaving in the slab, cache, heap
   reuse, bitmap and huge paths and left one plausible candidate (a
   `Purged` slab whose pages the kernel did not zero) with a checked-zero
   debug mode as the experiment that names it; it also found, on the way,
   a confirmed wrap to `len = 0xFFFF_FFFF` on the compaction path after an
   emptying GC (a crash, not this symptom; one line to fix).
2. **Several release-mode safety nets are `debug_assert!` only** and the
   release profile has integer overflow checks off, so on the project's own
   rule ("abort on any inconsistency, never continue") a corrupted cache
   header, a double `Meta::free`, or an underflowing counter continues
   silently in production. Promoting them is a day's work.
3. **The README and design claim four protections the binary does not
   have**: `mseal` sealing (probed, never called), `zero_on_free`,
   `slot_randomize` (parsed, never read), guard slabs on kernels without
   `MADV_GUARD_INSTALL` (silently zero), and `thp`/`cgroup`/`stats_print`
   tunables that do nothing. Cgroup awareness, goal number four, has no
   code at all.
4. **Two real detection gaps in the double-free story**: a duplicate pair
   that straddles the flush boundary is only half released, so the other
   copy can be handed out again with its bit clear; and the sized path
   accepts any slot start of a handed-out but uncommitted or guard slab.
5. **The fork handler misses three locks** added after the design was
   written (process stats, per-arena stats, the explicit-cache registry).
   Valkey forks for RDB and AOF rewrites; a child that inherits a held lock
   deadlocks on its first statistics call.
6. **Performance is at or past the goal on the target consumers.** Valkey's
   soak: write phase at parity or ahead, peak RSS +0.1%, post-delete RSS
   -2.4%, delete phase 3% behind with the mechanism named (the
   `malloc_usable_size` query on `zfree`'s path). Ruby: every row within
   noise of jemalloc, `erb_render` 11% ahead, RSS below jemalloc on every
   row but one. The Phase 0 set: ahead on 6 rows, parity on 4, behind by
   under 10% on the rest, with each remaining gap attributed to instruction
   count and dependent-load depth (structural, section 4).
7. **The mstress RSS row is structural and the recommendation is (d) in
   its whole-group form, scheduled after the correctness work**, with (c)
   as the fallback if it lands outside the band (section 4.4).
8. **The previous review's predictions held wherever a same-workload
   counter backed them and failed wherever they extrapolated** (section
   4.5). About one attribution in three made by the loop was later revised,
   always by a direct probe. The loop's own attribution rule (CLAUDE.md,
   added 2026-09-17) is the right one and should be enforced harder, not
   relaxed.

The recommended sequence (section 5): a short **release-readiness phase**
(correctness, release asserts, the fork handler, the two detection gaps,
truthful docs) before any more performance work; then Phase 1.5's close-out
with the mstress decision; then Phase 2 reordered so that `mseal`, the
double-free hardening the budget can afford, and cgroup awareness come
first; then the three prerequisites Phase 3 needs (a 64 KiB-page run, a
bare-metal `process_madvise` run, a long-lived Ruby soak).

## 1. State of the code

### 1.1 What was run, and the one failure

`make test` on the Mac dev container at `6a9016e` (host load average 4.9
to 7.3, other sessions active): 231 of 231 tests in the first process, 79
of 80 in the `api::` process. The failure:

```
api::ctests::mimalloc_test_stress
stress failed (ExitStatus(unix_wait_status(6)))
stderr: challoc-stress-792-42: /src/tests/mimalloc/test-stress.c:166:
        alloc_items: Assertion `p[i] == 0' failed.
```

`alloc_items` calls `calloc(items, 8)` and asserts every word is zero
before writing its cookie pattern; sizes are mostly 8..128 bytes with 1%
in the 800 B..51 KB range, 0.1% in the 8..512 KB range and 0.01% above.
The test runs 8 threads that are created and joined on each of 10
iterations. The same binary, rebuilt with the harness's flags and run
outside the suite, passed 54 times in sequence under five `MALLOC_CONF`
variants (default, `dirty_decay_ms:-1`, `tcache_compact_shift:0`,
`narenas:1`, `tcache:false`) and 96 times as 12 rounds of 8 parallel
instances (6 default, 3 with decay off, 3 with compaction off). The
failure therefore needs the scheduling the full suite produces (about 40
test programs compiling and running at once on an oversubscribed host) and
has a low rate even there; `make test` on both GCE VMs at `2c8731f` passed
(`bench/results/2026-09-18-phase-1.5-acceptance-3.md` section 1).

Two mechanisms produce this symptom: a slot or run flagged "known zero"
whose memory is dirty, or one slot handed to two threads (the second sees
the first's cookie). The flag's provenance is `CacheHeader.zeroed` (the
per-cache zero prefix, `src/heap.rs`), `class::Claim.zeroed` (true only
for the thread that moved a slab from `Fresh` or `Purged` to `Active`
under the class lock, `src/class.rs` `take`) and `huge::take`. The purge
paths flip state to `Purged` and discard under the same lock. A reading of
those paths in this session found the lock discipline sound; the ranked
candidates and the experiments that would settle them are in section 1.4,
from the dedicated reviewer. Two facts narrow it: progressive decay
(`2c8731f`, iteration 28) makes purges happen within the first 50 ms of a
run for cohorts of many slabs, where the flat 10 s window before it meant
nothing was purged during a short test, so the `Purged`-is-zero path is
exercised by this test for the first time since that commit; and the
test's thread churn exercises heap destruction and reuse from the metadata
free list every iteration.

What this means for the release: until the mechanism is named and a test
reproduces it on demand, the "memory safe" and "at least as secure as
jemalloc" goals are not demonstrated. This is the first item of section 5.

### 1.2 Simplification and hardening list, ranked by risk to a release

Each item: what, where, why it matters, what to do. "Verified" unless
marked.

**P0. Correctness and abort-on-inconsistency**

1. **The `calloc` race** (1.1). Root-cause with the experiments in 1.4;
   add the release assertions below first, since several of them turn a
   silent double hand-out into an abort with a message.
2a. **Compaction pop after an emptying GC wraps `len`** (section 1.4,
   confirmed): `pop_compact_run` calls `pop_top(cache, 0)` when
   `rebuild_run`'s `tick` flushed the whole cache and the rebuild returned
   early (`src/heap.rs:1339-1341`); `len - 1` wraps and the pop reads 32 GiB
   past the stack. Guard with the probe branch's `len == 0` refill; add the
   unit test. One line plus a test.
2. **Cache invariants are debug-only.** `run_end <= low_water <= len`
   (`src/heap.rs:60-62`, checked only in a test accessor at 262) is what
   keeps `pop_compact_run` from serving a stale pointer from
   `slots[run_end - 1]`; `refill`'s "cache is empty" (1767), `free_caches`'s
   "cache is flushed" (992) and `other_caches`'s "not the home arena"
   (1648) are `debug_assert!`. A violation is a silent double allocation, a
   silent leak of up to `cap` slots, or a split cache. All four are on cold
   paths; promote them to `assert!`.
3. **Integer overflow checks are off in release** (`Cargo.toml:33-38` sets
   `panic = "abort"` but not `overflow-checks`). `nslots - live`
   (`src/class.rs:1204`), `stats.empty -= 1` (1181, 1447), `HugeStats::
   sub_free` (`src/huge.rs:192-204`), `Table.count -= 1` (325),
   `AtomicBitmap::allocated` (`src/bitmap.rs:195-198`) wrap silently. With
   `live > nslots`, `take` reserves a wrapped count and `claim` spins
   4 million passes before `reservation_unmet` aborts. Set
   `overflow-checks = true` in the release profile, run `make quick` on
   both VMs (the fast paths have almost no arithmetic that can overflow; the
   `wrapping_*` calls that are intentional already say so), and keep it if
   the rows hold.
4. **`bin_stats` clamps `claimed - released` to capacity instead of
   aborting** (`src/class.rs:1595-1610`). It exists because `released` is
   read outside the lock, so a transient over-read is legitimate; but a
   permanent one (a bookkeeping bug) is hidden. Count clamp events and
   expose them in `malloc_stats_print`; abort when the clamp fires with the
   lock held.
5. **`State::from_u8` decodes every byte above 2 as `Purged`**
   (`src/slab.rs:48-56`), and `take` treats `Purged` as zero memory. A
   corrupted state byte becomes dirty memory from `calloc`. Abort on 4..255.
6. **`AtomicBitmap::release` checks the mask lies inside the slab's
   sub-word view only in debug** (`src/bitmap.rs:174`). In release a bad
   mask clears a neighbouring slab's bits. Promote; the caller already has
   the slab geometry.
7. **`Meta::free` cannot detect a wrong `Layout` or a double free**
   (`src/meta.rs:264-277`): it checks range and alignment only, so one
   block on two free lists is silent, and this is the allocator that hands
   out heaps and slot stacks. Reject a block equal to the current list
   head in release; poison and check the bin in debug.
8. **`Huge` descriptor table: duplicate key insert is debug-only**
   (`src/huge.rs:297`).

**P1. Detection gaps and lifecycle**

9. **Flush-boundary double free.** `flush` sorts the cache and releases
   the top `n` (`src/heap.rs:1805-1812`); `release_owned` aborts on a
   duplicate within the released batch (`src/class.rs:1341-1343`) and on an
   already-clear bit (1360-1364). If the two copies of a cached double free
   sit at indices `rest_len - 1` and `rest_len`, one is released (bit
   cleared) and the other stays cached; `malloc` then hands out a slot whose
   bit is clear, and a refill can claim it for a second owner. README
   footnote (1) says the cached case "is caught when the cache flushes the
   duplicates to the slab"; not in this case. Fix: one compare after the
   sort, `all[rest_len - 1] == all[rest_len]` aborts. Test: a negative mode
   that primes the cache so the pair straddles `cap / 2`.
10. **Sized path accepts never-committed and guard slabs.** `sized_slot`
    (`src/heap.rs:753-768`) checks the class hint and `is_handed_out`
    (the group watermark, `src/class.rs:719-721`). A slot start inside a
    `Fresh` slab of a handed-out group that is not yet committed, or inside
    a guard slab (whose body past the first page is read-write,
    `src/class.rs:960-967`), is pushed to the cache and a later `malloc`
    returns it. Cheap fix: `is_guard_slab` is arithmetic, and the arena's
    `committed` watermark is one load; check both on the sized fast path
    or on the flush. Test: `sdallocx(guard_body, size)` then `malloc` must
    abort, not return the guard memory.
11. **Fork handler misses three locks.** `fork_prepare` (`src/api/mod.rs:
    208-227`) takes the arena registry, class, set, table, huge, meta and
    background locks. It does not take `Shared.stats` (`src/heap.rs:432`,
    locked in `src/stats.rs:390, 416`), `Arena.stats` (`src/arena.rs:149`)
    or `Tcaches.lock` (`src/arena.rs:493`, which nests `meta`). A fork while
    another thread is inside `mallctl("epoch")`, `malloc_stats_print` or
    `tcache.create` gives the child a lock held by a thread that does not
    exist; the child deadlocks on its first statistics call. Valkey calls
    `epoch` every cron tick from the main thread, which is also the thread
    that forks, so the window is other threads (io-threads, modules); Ruby
    with threads calling `GC.stat` likewise. Add the three locks in nesting
    order and extend `fork_handlers_take_and_release_every_lock`.
12. **Thread-exit ordering.** `heap_destructor` (`src/heap.rs:1920-1933`)
    destroys the heap and then writes `TLS_EXITED`; a signal handler that
    allocates in between reaches a freed heap through `existing_heap`.
    Write the sentinel first.
13. **`free` can clobber `errno`.** `free_slow_in` runs `tick` (`src/heap.rs:
    1624`), which may start the background thread with `pthread_create`
    (`src/purge.rs:480`); glibc's thread creation can modify `errno` (the
    `clone3` fallback). Design 1 says `free` preserves `errno`, and nothing
    saves it. Save and restore `errno` around `create`, or start the thread
    only from allocation-side ticks. Suspected (not executed).
14. **Background-thread stack leaks per restart.** Each `create` reserves
    and commits a fresh 256 KiB stack that is never freed (`src/purge.rs:
    450-456`); `mallctl("background_thread", false)` then `true` in a loop
    grows metadata without bound. Keep one stack and reuse it.
15. **Owner array and `SlabDesc::arena` are two sources of truth**
    (`src/class.rs:929` and 936-937). `free` routes by the array;
    `page_group_is_idle` (1539-1550) trusts the descriptor. They are never
    cross-checked, and a disagreement would let one arena purge a page group
    another arena is claiming from. Assert equality once in `take_group` or
    delete the descriptor field (design 4 still lists it).
16. **Owner routing is bounds-checked but not semantically checked.**
    `Shared::owner` refuses indices above `MAX_ARENAS` but silently
    materialises an unbuilt automatic arena (`src/arena.rs:423-436`), and
    `free_other` creates an `others` node before anything validates the
    arena. Compare the owner word with `desc.arena()` once per slab switch
    in `release_owned` (the line is already touched by `dec_live`), and use
    a non-materialising lookup on the free path.

**P2. Claimed but not implemented, or implemented but silent**

17. **`mseal` is probed and never called.** `src/sys/features.rs:180`
    probes it; the only `sys::mseal` callers are the probe and a test.
    Design 10 step 5, design 14 ("Region table and reservations sealed with
    `mseal` when available"), the README kernel table and the layout
    diagram ("sealed after init") all claim it. Implement (the region table
    and `Shared` can be made read-only after init; the reservations'
    committed tails cannot be sealed, as the design already notes) or
    remove the claim until Phase 2 task 2.
18. **`zero_on_free`, `slot_randomize`, `double_free_scan`, `thp`,
    `cgroup`, `stats_print` are parsed, exposed through `opt.*`, and read by
    no code** (`src/config.rs:201-221`; `MADV_HUGEPAGE` is a constant with
    no call site). README's table lists zero-on-free and slot randomisation
    as "Opt-in"; only `double_free_scan` carries the "does nothing yet"
    footnote. Either implement (Phase 2 task 3) or make the README say
    "planned" and have `abort_conf` reject them.
19. **Guard slabs exist only when `MADV_GUARD_INSTALL` probes true**
    (`src/heap.rs:588`, interval forced to 0 otherwise). Design 14 lists
    them under "always on". On any kernel before 6.13 (and on Docker
    Desktop's 6.10, where every local test ran) there are no guard slabs.
    Say so in the table next to the kernel column, and add the missing
    end-to-end test: write past the last slot before a guard slab and expect
    the fault (today only the huge-run guard is tested, `negative.c`
    `huge_overflow`).
20. **`huge_retain_max` is not a tunable** (`src/huge.rs:56, 636`: a
    constant with a setter nobody calls; no config key, no `mallctl` leaf)
    though design 7 says "default 64 MiB".
21. **Class-order randomisation is not implemented**: design 2 says the
    relative order of classes is randomised; the code shuffles only the
    three top-level mappings (`src/layout.rs:638-656`) and puts class `c` at
    `c << lg_stride` (428). Per-class offsets do carry about 17.6 bits of
    entropy at the preferred layout (665). Fix the design text.
22. **`lazy_free` is unprobed**: the probe issues `MADV_DONTNEED` only
    (`src/sys/features.rs:194-209`); under `lazy_free` a kernel that
    refuses `MADV_FREE` through `process_madvise` fails every batch and
    redoes it as a loop. Correct but a silent tax; probe the configured
    advice.

**P3. Seams to simplify**

23. **"Which classes are cached where" is encoded four times**:
    `Config::cache_cap` (above `tcache_max` gives 0), `other_cache_cap`
    (above `NBINS` gives 0), `free_other`'s own `class >= NBINS` test
    (`src/heap.rs:1609`), and `alloc_slow`'s `size() > tcache_max` reroute
    to arena 0 (1538-1551). `alloc_other` bypasses the rule in
    `ensure_cache` and creates a 3.4 KiB `others` node for a class that
    will never be cached there. One `Config::cap_for(home, arena, class)`
    and one routing decision.
24. **`MALLOCX_ARENA(home)` for a class above `tcache_max` lands in arena
    0** (`alloc_in` at `src/heap.rs:1217-1222` falls into `alloc_slow`'s
    override), contradicting design 13.3 ("`MALLOCX_ARENA` allocations keep
    their arena") and per-arena `large` statistics. Valkey 9.1.2 never uses
    `MALLOCX_ARENA` (checked in its `zmalloc.c` and `allocator_defrag.c`:
    only `MALLOCX_TCACHE_NONE`), so no consumer is affected today. Route
    `alloc_in` misses to `alloc_slow_in(arena)` directly.
25. **`mode` and `compact_mask` encode one state in two fields** written
    together at three sites; `MODE_OFF` still routes one pop in 2^32
    through `pop_compact`. Derive the mask from the mode on the cold path.
26. **The decay step gate is duplicated line for line** in
    `ClassState::decay` (`src/class.rs:1562-1585`) and `Huge::decay`
    (`src/huge.rs:1103-1123`), with `oldest_empty`/`next_decay` in both
    structs. Lift into `purge::Decayer` with a walk callback; the walks
    themselves differ legitimately.
27. **`set_arena`'s fallback drops thread byte counters** (`src/heap.rs:
    1038-1040`): when no `others` node can be allocated it frees the home
    caches without folding `stats()` into `uncached`, unlike
    `set_tcache_enabled(false)`. One line.
28. **`getrandom` on every heap creation for an unused RNG** (`Heap::rng`,
    `next_random`: no callers; `os::seed()` at `src/heap.rs:943`). A syscall
    per thread start, for `slot_randomize`, which does not exist. Remove or
    seed lazily.
29. **`curslabs = committed - empty - purged` is computed at four sites**
    (`src/class.rs:1607, 1671`, `src/stats.rs:317`, `src/api/mallctl.rs:
    477`); `Heap::uncached` is bumped in three shapes. One accessor each.
30. **Huge-run page accounting uses two formulas** (`usable_pages(size) +
    GUARD_PAGES` at alloc, `run.pages` at free, `src/heap.rs:891-903`), and
    `stats.rs:342`'s `saturating_sub` suggests the drift was seen. Read the
    pages from the descriptor the allocation just created. Suspected.
31. **Vestigial**: `ClassState::check` and `SlabTable::check` (test-only
    callers), `Lock::try_lock`, `Class::tier`, `Heap::slow_ticks`,
    `Tcaches::len`, unused `MAP_*`/`MADV_*` constants in `src/sys/mod.rs:
    39-64`. `SMALL_SLAB_BELOW`'s three slab tiers are all reachable and
    stay. Page groups are live, not dormant: since `LG_MIN_SLAB = 12` any
    16 KiB or 64 KiB page kernel commits, guards and purges 4 KiB slabs in
    groups; the test doc at `src/class.rs:1908-1909` ("Dormant while the
    minimum slab is 64 KiB") is wrong.
32. **History in hot-path module docs** (`src/heap.rs:12, 36`, `class.rs:
    488`, `layout.rs:33`, `huge.rs:35, 373` "per arena in Phase 1",
    `heap.rs:1897` "stats merging and cgroup sampling join in later
    tasks"): the iteration log leaking into the code. Replace with what the
    code does; the log is PROGRESS.md.
33. **Stale prose**: `src/heap.rs:8-10` and `855` say `free` touches "one
    word of the slab descriptor"; since task 4f it reads a bitmap word and
    an owner word and never the descriptor. `src/api/cxx.rs:22` says sized
    `delete` ignores its size "as `free_sized` does in Phase 0"; `free_sized`
    now aborts on a mismatch. `src/tls.rs:115` says the TLS exports "may be
    removed once heaps exist"; every C test's `require_challoc` depends on
    `challoc_tls_get`. `PIDFD_SELF` is dated 6.16 in `src/sys/mod.rs:79-82`
    and 6.14 in `src/purge.rs:149` and design 8. Abort messages read
    `challoc: challoc: ...` at `src/sys/mod.rs:516, 535`, `src/api/mod.rs:
    167, 193, 201`, `src/api/jemalloc.rs:117`.
34. **Complexity**: no function in the four core files exceeds about 85
    lines, but `Heap::pop_compact` (`src/heap.rs:1281-1328`, depth 6, and
    the only refill outside `alloc_slow_in`), `ClassState::claim` (1094-
    1158, retry loop inside pick loop inside plan loop), the two
    `purge_curve` walks, and `rebuild_run`'s block swap (1421-1429) would
    each be safer as two functions with the invariant at the seam.

**P4. Drop-in and packaging** (from the API surface reading)

35. **The plain `libchalloc.so` has no SONAME** (asserted absent at
    `src/api/ctests.rs:651`) while Valkey links `-lchalloc`: an unversioned
    ABI for a distro package. Give it `libchalloc.so.0`.
36. **Valkey needs `quantum8`, Ruby's stage is `quantum16`**: two
    binaries; one system library cannot serve both. Phase 3 must decide
    (jemalloc ships one `lg_quantum` per build too; Wolfi's Valkey vendors
    its own).
37. **Wolfi's `-Wl,--as-needed`** can drop `DT_NEEDED libjemalloc.so.2`
    for a link-only consumer that references no jemalloc symbol, which
    then silently runs on glibc malloc. Ruby's `malloc_conf` read keeps the
    reference; the melange pipeline should `readelf -d` the result.
38. **Sized `operator delete` ignores its size while `free_sized` aborts
    on a mismatch** (`src/api/cxx.rs:170-174` vs `src/api/libc.rs:187`):
    safe, inconsistent, and the sized fast path goes unused for C++.
39. **`malloc_trim(0)` is a full process-wide purge** ignoring decay age
    (`src/api/libc.rs:383-389`); Ruby's GC calls it after every full GC,
    which under jemalloc was a no-op. RSS looks good; the refault cost is
    unmeasured. Measure in `ruby-bench`; consider honouring the decay curve
    for `pad > 0`.
40. **Stricter than jemalloc on misuse**: `sdallocx`/`free_sized`
    mismatch, `malloc_usable_size`/`realloc`/`sallocx` on a freed or foreign
    pointer all abort where jemalloc is undefined. Correct by design; a
    Valkey module or Ruby C extension leaning on jemalloc's leniency dies
    with SIGABRT. Say so in the release notes.
41. **`opt.tcache_max` is typed `unsigned`** where jemalloc's is `size_t`;
    `opt.<compat key>` returns ENOENT though design 12 says every key is
    readable; `thread.arena` written with an unbuilt automatic arena returns
    EFAULT where jemalloc builds it; `arena.<i>.destroy` leaves the arena
    usable; `je_pvalloc` is missing; `MALLCTL_ARENAS_DESTROYED` is declared
    in the header and unimplemented. None used by Valkey or Ruby.
42. **`challoc_tls_set` is an exported write primitive to the heap
    pointer** in a hardened allocator, kept for tests. Replace both TLS
    exports with a `challoc_version()` probe.
43. **Untested API**: `je_memalign`, `je_valloc` (symbol presence only),
    `free_sized` positive path from C, `xallocx` with `extra`,
    `malloc_trim` with nothing purgeable, `malloc_stats_print` never
    allocating (a `thread.allocated` delta would prove it), `dallocx(p,
    TCACHE_NONE)` twice, `realloc`/`sallocx` on a stale pointer, a free
    into a guard gap, a `free_sized` with a huge-sized hint on a slab
    pointer.

### 1.3 Unsafe code

Every `unsafe fn` in the core files carries a `# Safety` section and
`#![deny(unsafe_op_in_unsafe_fn)]` is on (`src/lib.rs:14`). About 85
`unsafe` sites were sampled across the reviews; the ones whose comment no
longer describes the code:

- `src/heap.rs:1971-1985` `existing_heap` and `1936-1946` `heap_for_thread`

### 1.4 The `calloc` failure: candidates

A dedicated reading traced every path that sets the "known zero" flag or
hands out a slot, through the eight areas a race could hide in: the
`plan`/`take`/`on_live_zero`/purge protocol, the cache prefix arithmetic
under GC and compaction re-entered from inside a pop, thread exit and
heap reuse from the metadata free list, the sub-word bitmap views, `Fresh`
slabs, the huge allocator's `take` and coalescing, batch range merging,
and the sized path. **No interleaving in today's code was found that
returns a zero-flagged dirty slot or hands one slot to two threads.** The
slab protocol (reserve `live` under the class lock before claiming bits;
clear bits before `sub_live`; purge only `Empty` slabs with `live == 0`;
flush the discard batch before the lock drops) is sound as written, and
the zero prefix keeps `slots[i]` zero for every `i < min(zeroed, len)`
through each of its six writers. That leaves:

- **Plausible, not excludable by reading: `Purged` memory that is not
  actually zero.** `take` reports zero for a `Purged` slab on the strength
  of the discard having zapped the pages (`src/class.rs:1220-1222`). The
  failing run was on Docker Desktop's 6.10 LinuxKit kernel, where Docker's
  seccomp profile makes the `process_madvise` probe fail and every purge
  goes through the `madvise` loop (PROGRESS.md notes), so the batch path
  is not the suspect there; a partial or delayed `MADV_DONTNEED` effect on
  that kernel under load is not something the code can rule out, and the
  progressive decay is what first made purges happen inside a short test.
  This is the candidate the experiments below are designed to name or
  kill.
- **Confirmed, a different symptom: a wrap to `len = 0xFFFF_FFFF` on the
  compaction path.** `pop_compact_run` with `run_end == 0` calls
  `rebuild_run` (`src/heap.rs:1339-1341`), which runs `tick` and therefore
  the cache GC; with `low_water == len <= 3` the GC flushes every entry
  (`lw - lw / 4 == lw`), and `rebuild_run` then returns early if the class
  is no longer fragmented or the claim gets nothing. `pop_compact_run`
  re-reads `len` (0), finds `run_end` still 0, and calls `pop_top(cache,
  0)`, whose `len - 1` wraps in release and reads `slots[0xFFFF_FFFF]`. The
  probe-mode branch guards exactly this case with a refill (1301-1308); the
  compact-mode branch does not. The result is a wild read 32 GiB past the
  stack, a fault rather than a dirty slot, so it is not the observed
  failure, but it is a release-blocking bug on its own (P0 item 2a below).
- **Excluded with the evidence written down** (the reading's report has
  the line-by-line argument for each): the claim/release/purge protocol;
  every writer of the cache prefix; heap destruction and reuse (every
  `CacheHeader` field is rewritten by `create_detached` and
  `ensure_cache`, flushed caches keep no bits); the sub-word masks; `Fresh`
  slabs (`SlabDesc::init` runs only in `take_group` for never-handed-out
  slabs); the huge `take` flag and coalescing rule; batch merging; the
  sized path (the stress test frees with plain `free`).

The experiments, in order of information per hour:

1. **A checked-zero mode.** In `ClassState::claim`, after the bit loop for
   a pick with `zero`, and in `Huge::take` when returning `zeroed = true`,
   read the first and last word of each claimed slot (or page) and abort
   with class, slab, prior state, discard backend and the offending word,
   behind a `MALLOC_CONF` key or `debug_assertions`. Loop the stress test
   under the full concurrent `cargo test api::` load until it fires. The
   message says whether the slab was `Purged` (the discard path) or
   `Fresh` (the commit path), which is the one bit the C assertion cannot
   give.
2. **Configuration bisect under the same load**: `dirty_decay_ms:-1` (no
   purging: if the failure vanishes, the discard path is it),
   `tcache_compact_shift:0`, `narenas:1`; several hundred iterations each,
   with `uname -r`, the probe line and the THP setting recorded. This
   session's 150 standalone and parallel reruns of the same configurations
   are consistent with a rate too low for that sample, not with an
   exclusion.
3. **Fix the confirmed wrap regardless** (a `len == 0` check after
   `rebuild_run`, mirroring the probe branch, plus a unit test that puts a
   compact-mode cache at one entry with the GC due and pops).

### 4.2 Why each behind row is behind, and whether an iteration is worth it

- **larson 1 and 10 threads on aarch64 (+6%)**: instruction count and
  dependent-load depth. `malloc` is GOT, TLS slot, heap, header, slot (five
  dependent loads) where jemalloc's bin lives in the static TLS block
  (three); challoc executes 4..5% more instructions per operation; L1 dTLB
  refills are 3.17 against 1.74 per operation after the dense headers
  (`2026-09-17-gce-review-counters.md` 2.3, 3.3; `2026-09-18-aarch64-gce-
  dense-headers.md`). Structural: the remaining lever is moving the stack
  tops into the TLS block (design 6.1 change, `.tbss` growth). Not worth an
  iteration for the goal: larson is a proxy, and Valkey's main thread is at
  parity.
- **larson 16 threads on x86_64 (+9.2%)**: the same instruction count
  amplified by hyperthread pairs (244 against 225 instructions per
  operation; `2026-09-18-phase-1.5-acceptance.md` counter section).
  Structural; inside the band.
- **alloc-test (+5%)**: instruction count, IPC higher than jemalloc's
  (`review-2026-09-17.md` 2.2). Structural; inside the band.
- **valkey1 on aarch64 (+9.4%) and the soak's delete phase (+3%)**: one
  mechanism, named and measured: Valkey's `zfree` calls
  `malloc_usable_size` before `sdallocx`, and the query's slow-path form
  (`Regions::classify`, then the table, then the bitmap word) has more
  dependent loads than the `free` fast path; 206 against 96 cycles per
  command in the delete phase after the dense bitmap (`2026-09-18-aarch64-
  gce-sized-free.md` 4.3; `2026-09-18-aarch64-gce-dense-bitmap.md`). This
  is the one remaining gap worth an iteration: it is on the target
  workload, it has a per-operation attribution already, and the fix
  (`usable_size` reading its geometry from the dense arrays like the `free`
  fast path, keeping the bit test) does not change what is checked. The
  plan's Phase 1 soak criterion ("at least equal") is formally unmet in the
  delete phase until it lands.
- **glibc-simple on x86_64 (+6.1%)**: the row swings 18 points between
  commits that touch nothing it exercises. Not actionable; the scorecard
  should carry its noise band.
- **mstress RSS**: section 4.4.
- **Ruby `gc_churn` peak RSS (+4.8% / +1.2%)** and the note that a 10 s
  decay window never fires in a 1.6 s process: not a regression, a
  coverage gap (4.3).

### 4.3 Coverage gaps

- **64 KiB-page aarch64 hosts.** Wolfi builds jemalloc with `lg_page=16`,
  so Wolfi expects 64 KiB aarch64 kernels (plan, Phase 3 prerequisite).
  challoc's 4 KiB slabs for the 512..1024-byte classes make page groups a
  live path on such a host (commit, guard and purge in groups of 16 slabs);
  it has run only under a faked page in `class::tests`, and the `huge.rs`
  tests hard-code `PAGE = 4096` (`src/huge.rs:1272, 2068`) and would fail
  there. Nothing in the harness targets it. Recipe: Ubuntu 24.04 arm64 has
  `linux-generic-64k`; a second, throwaway C4A VM (not the reference VM,
  whose kernel must stay comparable) with that kernel running `make test`,
  `make fuzz` and the Valkey `memefficiency` stage is an afternoon. Also
  untested: the 39-bit-VA aarch64 minimum layout (about 435 GiB of a 512 GiB
  user space, `src/layout.rs:590-607`).
- **Long-lived Ruby.** Every Ruby row is under 6 s; `dirty_decay_ms` never
  fires and Ruby with jemalloc never calls `malloc_trim`. Wolfi's aarch64
  jemalloc returns 48% after 10 full GCs where challoc returns 2%
  (`2026-09-17-aarch64-ruby.md`). A Rails or Sidekiq process is where the
  post-burst residency would show. Missing: a Ruby soak row (minutes, with
  RSS sampled), and a decision on `background_thread` for Ruby-shaped
  consumers.
- **Valkey with io-threads above 1.** The suite's `unit/io-threads` passes;
  the soak runs the default single io-thread. With io-threads the frees of
  one thread's allocations land in another thread's cache (`others` nodes)
  or, through the sized path, in the home cache with routing at the flush.
  That path is measured only by xmalloc-test. Missing: one soak with
  `io-threads 4`.
- **Fork-heavy consumers.** Valkey's suite forks for RDB and AOF under
  load and passed; `fork_alloc.c` and `fork_signal.c` cover the handlers;
  but item 11 (three locks not taken) shows the handler is not audited
  against the lock inventory, and nothing tests fork while a second thread
  is inside `mallctl`.
- **Containers with memory limits.** Nothing: no `src/sys/cgroup.rs`, the
  `cgroup` key is inert, `stats.cgroup.*` is asserted to be an invalid
  name (`src/api/mallctl.rs:1086`), the background thread has no PSI path.
  Goal number four has zero code and Phase 2 tasks 4 to 7 are untouched.
- **Bare-metal `process_madvise`.** Every local purge runs the `madvise`
  loop (Docker's seccomp denies `process_madvise`); the batch path runs
  only on the GCE VMs' kernel 7.0. One run on a bare-metal 6.14+ kernel
  before Phase 3 (PROGRESS.md already asks for it).
- **`dlopen` of challoc after start**: unsupported by design, undetected
  in code, undocumented in README.

### 4.4 The mstress question

The row: mstress at 16 threads on x86_64, +19.1% RSS (341.5 against 286.8
MiB), aarch64 +9.8%. `2026-09-18-phase-1.5-acceptance-3.md` 3.1 shows the
mechanism: a 0.63 s process in which no decay window acts (jemalloc's RSS
is the same with decay off), `narenas:1` equals jemalloc's RSS, and the
+60 MiB at 16 thread arenas plus arena 0 is `Empty` small slabs (+18),
partial small slabs (+9), touched pages of `Empty` medium-class slabs
(+21) and per-arena metadata (+9.5) that only the owning arena and class
can reuse, where jemalloc's one dirty extent pool per arena serves every
bin and every large size. On the same row challoc is 40% faster than
jemalloc (0.63 against 1.05 s): jemalloc pays for its shared pool in time.

The options on record, and this review's reading:

- **(b) a per-arena dirty budget purged at once beyond it** (jemalloc 4's
  `lg_dirty_mult`): `dirty_decay_ms:0` prices the refaults at 0.63 to 1.12 s
  wall on this row; a purge-on-threshold policy is one the soak's write
  phase would pay for on every burst. jemalloc 5 removed it for that
  reason. **Reject.**
- **(d) an `Empty`-slab handoff between arenas on the fresh-commit path.**
  Right mechanism, wrong granularity as written: since task 4f a bitmap
  line and a descriptor line belong to one arena so that the `free` check
  never reads a line another arena writes. Lending one slab of a group
  breaks that invariant and brings back the coherence traffic the arena
  default removed. The design-consistent form is a **whole-group
  handoff on the `take_group` path**: when an arena needs a new group of a
  class, it first looks for a group of that class, owned by another arena,
  whose every slab is `Empty`, `Purged` or `Fresh`, and takes it over
  (rewrite the owner word and the descriptors' arena field under both
  arenas' class locks in index order, move the set bits). For the small
  classes `slabs_per_line` is 1, so a group is one slab and this is (d)
  exactly; for the 4 KiB-slab classes a group is 128 slabs and only fully
  idle groups move, which is the honest version of the same idea. It
  touches the commit slow path only, keeps every hot-path invariant, and
  attacks the +18 and +21 terms; the partial-slab and metadata terms stay,
  so the row should land at about +8..10% on x86_64 and inside the band on
  aarch64. It also changes design 13.3's ownership sentence to "an arena
  owns its groups until it lends an idle one", and per-arena statistics
  move with the group. Verification: the mstress row on both VMs with the
  `arenasample` probe (expect `Empty` small slabs near the `narenas:1`
  figure), `quick` and the larson10 L1D column unchanged (the invariant is
  the point), the memefficiency stage, and the scorecard.
- **(c) accept and document.** The row is a 0.63 s, 16-allocating-thread
  synthetic; neither target consumer has that shape (Valkey's allocating
  threads are the main thread plus io-threads, Ruby's are GVL-serialised),
  and the same run shows challoc 40% faster in time. If the human wants
  Phase 1.5 closed now, this is defensible: record the row as the measured
  price of per-class regions at 16 arenas, with the attribution file as
  the evidence.

**Recommendation: (d) in the whole-group form, scheduled after the
release-readiness work of section 5, with (c) as the fallback if the
protocol run still lands outside the band.** The human can accept or
overrule this in one line. What should not happen is (d) landing before
the correctness items: it is the largest change to ownership since task
4f, and the `calloc` failure has to be understood first.

```
  e. A melange pipeline check that DT_NEEDED names the library.
```

### 5.3 What the loop should stop doing

- **Stop landing design changes on an attribution made on another
  workload or without a run-shape check.** The record (4.5) is that one
  cause in three was revised, always by a direct probe; the progressive
  decay commit is the example. The CLAUDE.md attribution rule should
  extend from fast-path changes to any change made to pass a criterion.
- **Stop rerunning the full 13-minute protocol set per iteration when no
  fast-path line changed.** `quick` plus the scorecard is the trend; the
  protocol run belongs to acceptance. Three acceptance reruns produced the
  same mstress number with the same attribution twice.
- **Stop adding tunables before their code exists.** Five keys are inert
  today and two are advertised as protections.
- **Stop appending everything to PROGRESS.md.** It is 232 KB and every
  iteration reads it in full. Move Phase 0 and Phase 1 decisions to
  `docs/decisions.md` (they are the durable record) and keep PROGRESS.md
  to the open phase; keep the "Notes for the human" as the human's
  mailbox, pruned when answered.
- **Stop writing iteration history into hot-path module docs.** The
  module doc says what the code does; the log says how it got there.
- **Stop treating the Phase 0 RSS rows as acceptance for consumers the
  rows do not resemble** without saying so; keep them as trend rows and
  criteria for the loop, and let the human decide (c)-type questions with
  the consumer shape in front of them.
- **Stop reporting "PASS on substance" for a criterion whose literal
  reading fails** (criterion 4's rank reading, acceptance run 1) without
  the human's word; the run 1 note did flag it, which is the right
  behaviour, and the criterion text should then be fixed.

And what it should keep doing: the per-operation attribution before a
fast-path change, the results file per step, the churn and arenasample
probes, the scorecard per landed commit, and the "Notes for the human"
mailbox, which is where every decision in this review was already waiting.
