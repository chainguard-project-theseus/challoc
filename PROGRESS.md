## Design decisions

- Phase 2 task 2 (2026-09-18), what `mseal` seals: only the never-committed parts of the three reservations (`Regions::never_committed`: the gap on either side of every class region as one contiguous range per gap, `NCLASSES + 1` of them, and the alignment-plus-slide slack before and after the huge and metadata regions; 57 ranges at quantum 16, `MAX_SEALED = NCLASSES + 5`), one `mseal` call per range, right after `Regions::reserve` in `api::init`, gated by the probe's `Features.mseal`. Not sealed, and why: the class regions, the huge region and the metadata region are `mprotect`ed on commit and `MADV_DONTNEED`ed on purge for the life of the process, and `mseal` forbids exactly those (the design's "reservations" is read as "what never changes protection"); the huge-run guard pages in `PROT_NONE` fallback mode are re-committed on reuse; the region table is `Shared.regions`, a field of a static in the library's own data segment that shares its pages with locks and counters written at run time, in a mapping `ld.so` owns, and `mseal` does not stop writes anyway. Design 2, 10 (step 5, steps renumbered) and 14 and the README row now say exactly this.
- Phase 2 task 2 (2026-09-18), a refusal after a successful probe stops the sweep and does not abort: sealing is a hardening extra, not a heap invariant (`ENOMEM` at `vm.max_map_count` in a process with tens of thousands of VMAs would otherwise kill it at init). The count is observable: `malloc_stats_print` prints `Sealed ranges: N of M`, `api::sealed_ranges()` for tests.
- Phase 2 task 2 (2026-09-18), tests find sealed VMAs through `/proc/self/smaps` (`sl` in `VmFlags`, kernel 6.10+), not through allocator internals, and skip with a message where the program's own `mseal` probe fails: Docker's default seccomp profile filters the syscall on the Mac (EPERM) and on the GCE VMs' Docker 29.1 (ENOSYS: libseccomp does not know it), so on both hosts `make test DOCKER_FLAGS='--security-opt seccomp=unconfined'` is the run that exercises sealing; `make test` alone exercises the skip path and asserts nothing is sealed. The Rust layout test forks: a sealed layout can never be released and a second full layout must not stay alive in the test process.
- Phase 1.5 task 14 (2026-09-18), `check_live` takes the located slab and slot and loads the watermark `Relaxed`: `Regions::classify` already computed slab and slot from the dense arrays for every query, and `locate` recomputed them from the table line (a second dependent chain in front of the bitmap word, `bench/results/2026-09-18-aarch64-gce-usable-size-chain.md` 1.2). The relaxed load uses `desc_if_committed`'s argument unchanged (a live slot's group words are visible through the program's own ordering; any other pointer aborts on every observable value); `free`'s slow path (`classify_free` -> `check_located`) shares the function, so its watermark load is relaxed too, which changes no outcome (the abort names may differ only for an invalid pointer racing a hand-out). The guard-slab test runs in the cold abort path only: guard slabs never have a bit set (`take_group` leaves them zero), so the bit test catches them and `not_live` picks the `guard slab` message as before; this removes a 32-bit `udiv` from every query.
- Phase 1.5 task 14 (2026-09-18), `valkey_model -u` / row `valkey1-usable`: the attribution rule needs a per-operation number on a workload that calls the query, and neither `valkey1` nor `valkey1-free` does (the model freed through `sdallocx`/`free` alone). `-u` calls `malloc_usable_size(p)` before every free, which is Valkey's `zfree(ptr)` (`zmalloc_size`, then `je_sdallocx`); the row is for `quick-perf`/`ab` attribution and is not in the `quick` gate's default set or the scorecard, so no existing number moves.
- Phase 1.5 task 13 (2026-09-18), SONAME: the plain build carries `libchalloc.so.0` (`build.rs` always emits `-Wl,-soname`; the `jemalloc-soname` feature selects `libjemalloc.so.2` instead). Reason: Valkey links `-lchalloc` and a distro package needs a versioned `DT_NEEDED`; `.0` is the ABI major of a 0.x crate. Cargo still writes the file as `libchalloc.so`, so `contrib/valkey/build.sh` makes the `libchalloc.so.0` link beside it (the binary's `RUNPATH` is that directory) and checks `DT_NEEDED [libchalloc.so.0]`; `ctests::jemalloc_compat_stage` asserts the plain soname; `scripts/jemalloc-compat.sh` and its `libjemalloc.so.2` check are unchanged; every `LD_PRELOAD` path is a file path and unaffected. Design 13.6.
- Phase 1.5 task 13 (2026-09-18), one library or two for quantum8/quantum16: one quantum per build stays (the class table is compile time, as jemalloc's `lg_quantum` is; a run-time quantum would put a table select on every class lookup and change the tested builds). The Phase 3 rule (design 13.6, plan Phase 3 task 2): the system `libchalloc.so.0` and the compat `libjemalloc.so.2` are `quantum16`, because Wolfi's `jemalloc` 5.3.1 is configured without `--with-lg-quantum` (checked in `wolfi-dev/os` `jemalloc.yaml`: `--enable-xmalloc --prefix=/usr --with-lg-page=$_pgs --with-lg-hugepage=21`), i.e. jemalloc's default quantum 16 on both architectures, which is the class table Ruby and every other consumer of the system jemalloc already runs on; Valkey, the one `quantum8` consumer (defrag asserts `arenas.quantum == 8`, from its bundled jemalloc's `--with-lg-quantum=3`), gets a private `quantum8` build in its own package under `/usr/lib/valkey/` (named in `RUNPATH`, which is what `contrib/valkey/build.sh` does today with `-Wl,-rpath`) or statically from `libchalloc.a`, the way Wolfi's Valkey builds its bundled jemalloc today. Two libraries with one soname cannot share `/usr/lib`, so the system library is never `quantum8`. Nothing in this repository's tested builds changes.
- Phase 1.5 task 13 (2026-09-18), `challoc_tls_get`/`challoc_tls_set` removed, `challoc_version()` added (`src/api/mod.rs`): returns the crate version (`CARGO_PKG_VERSION`, `0.1.0`) as a NUL-terminated static string, not `mallctl.rs`'s `VERSION_STR`. Reason: `VERSION_STR` is the jemalloc-shaped `5.3.0-0-gchalloc` that exists for parsers of `mallctl("version")` and is not challoc's version; the probe's job is to say that challoc is loaded and which challoc, and the soname major follows the crate major. It reads and writes no allocator state and does not initialise. `tls.rs` asserts neither TLS accessor is a dynamic symbol and that `challoc_version` is; `require_challoc` in `tests/c/common.h`, `cxx_new.cpp`, `libc_api.c` and `tests/glibc/test-skeleton.c` `dlsym` it (the fuzz driver and the mimalloc stress use `common.h`). `tests/c/tls_threads.c` no longer drives the slot: each of 64 threads reads `thread.allocatedp` (the counter's address inside its heap), checks `thread.allocated` moves by its own block's usable size (the pointer's value is stale until that read, as the Rust test documents), and the main thread checks the 64 addresses are distinct and not its own, under a barrier so no heap is reused before it is observed. `tests/c/fork_signal.c` used `challoc_tls_get() == NULL` to prove challoc had not initialised before `main`; it now proves the property that check guarded: the SIGALRM handler records whether it ran inside one of the program's own atfork handlers (`in_atfork`/`ran_inside`), which happens only when the raise was not blocked, i.e. challoc's prepare had not run yet (handlers registered in the wrong order) or did not block signals; `CHECK(ran_inside == 0)` per round.
- Phase 1.5 task 13 (2026-09-18), sized `operator delete` routed through the sized path (`src/api/cxx.rs`): `_ZdlPvm`/`_ZdaPvm` are `free_sized(p, size)`, `_ZdlPvmSt11align_val_t`/`_ZdaPvmSt11align_val_t` are `free_aligned_sized(p, align, size)`, so the hint is `class_for(size, align)`, the same class the matching `new` (`malloc`/`aligned_alloc`) took, and a mismatch aborts as `free_sized` does; the unsized aligned forms stay plain `free`. Reason: explicit and independent of the `libc` crate version; the header check keeps them honest on both arches.

Reason: mirrors glibc's `abort` so a handler or blocked mask cannot let the process continue past an inconsistency.
- Phase 0 task 2: Linux-side coverage for `sys` is Rust unit tests under `cargo test --features std` run inside the container (mmap/mprotect/madvise, mseal, process_madvise, prctl, getrandom, futex, clocks, files, abort in a child process). Reason: no exported entry points exist yet to drive from C via `LD_PRELOAD`.

- Phase 0 task 3: page size comes from libc's `getauxval(AT_PAGESZ)` (design section 10 step 1), falling back to parsing `/proc/self/auxv` with our own syscalls, then abort. Reason: guessing a page size would corrupt every mapping; `getauxval` never allocates and is how glibc's malloc learns it.
- Phase 0 task 3: every probe treats any error as "unavailable", and `process_madvise` is probed with `MADV_DONTNEED` and checked for effect (whole page reported, page reads zero). Reason: failure modes vary (ENOSYS, EINVAL, EPERM, EBADF); DONTNEED is what purge issues and older kernels accept other advice but not it.
- Phase 0 task 3: `process_madvise` falls back from `PIDFD_SELF` to `pidfd_open(getpid())` and keeps that fd (`ProcessMadvise::Pidfd`); `Features::release()` closes it for the fork child, which must re-probe. Reason: the pidfd names the parent after fork.
- Phase 0 task 3: the `mseal` probe seals a `PROT_NONE` scratch page and leaves it mapped. Reason: a sealed page cannot be unmapped; PROT_NONE costs one VMA and no RSS, and it proves sealing rather than just the syscall's existence.
- Phase 0 task 3: `MADV_COLLAPSE` is not probed eagerly. Reason: a reliable probe needs a populated 2 MiB-aligned region and THP `always`/`madvise`; design section 10 already defers THP to the `thp` tunable, so its probe belongs with that work (Phase 2 task 5).
- Phase 0 task 4: the TLS slot symbol is `.globl` + `.hidden`. Reason: hidden keeps it out of the dynamic symbol table so the only dynamic relocation is the `TPOFF64`/`TLS_TPREL64` GOT fixup and nothing can interpose it; it still has to be global because debug/test builds place the `global_asm!` in a different codegen unit from the accessors.
- Phase 0 task 4: `challoc_tls_get`/`challoc_tls_set` are permanent diagnostic exports, and `tests/c/tls_threads.c` finds them with `dlsym(RTLD_DEFAULT)`. Reason: no heap exists yet so a C program under `LD_PRELOAD` needs some way to drive the slot, and a separate test-only `.so` build would double the fat-LTO build; dlsym keeps the test binary free of a link-time dependency and lets it prove it fails without the preload.
- Phase 0 task 4: `make test` runs `cargo build --release` before `cargo test`, and tests that need the `.so` fail with a message if it is missing rather than building it themselves. Reason: a test spawning `cargo build` would contend with the running `cargo test` for the target-dir lock.
- Phase 0 task 5: class stride is 4x the region (gap 3x) so `c = (p - superblock) >> lg_stride` is a shift; the region halves from 2^38 to 2^32 on `mmap` failure, and as a last resort the stride drops to 2x the region (gap 1x) before aborting. Reason: design 2 wants a power-of-two stride, and 3x is not one; the 1x gap is below the 1.25x minimum but keeps a 39-bit-VA kernel working rather than failing outright.
- Phase 0 task 5: the superblock and every class base are aligned to `MAX_SLAB` (4 MiB, the 256 KiB class's slab), and per-class random offsets are multiples of it. Reason: `offset = p & (slab_size - 1)` in design 3 is only correct when the class base is aligned to its slab size; one alignment for all classes is simplest and is THP-friendly.
- Phase 0 task 5: region bases come from the kernel's mmap placement plus a random reservation order for the three mappings, a random `MAX_SLAB`-granular offset inside each class gap, and a random 1 GiB slide of the huge and metadata bases inside an over-reserved window. Reason: design 2 asks for getrandom-randomised bases; a `MAP_FIXED_NOREPLACE` search for arbitrary bases can fail unpredictably, whereas sliding inside a reservation cannot.
- Phase 0 task 5: the `>> 32` reciprocal is kept as designed even though it is only exact for offsets that are multiples of the slot size. Reason: `free` only needs exactness on slot starts, and a misaligned offset can never satisfy `slot * size == offset` for any `slot`; the exhaustive host test over every in-slab offset of every class confirms it.
- Phase 0 task 5: `class_of(0)` is class 0 (one quantum). Reason: `malloc(0)` must return a unique pointer and the smallest slot is the cheapest way.
- Phase 0 task 5: `Regions::release` (munmap of all reservations) exists as a public unsafe method. Reason: the Linux tests reserve twice in one process to check randomisation; the allocator itself never calls it.
- Phase 0 task 6: `AtomicBitmap` keeps the padding bits above `nslots` in the last word permanently set (`init`). Reason: a set bit already means "not claimable", so refills can never hand out a non-existent slot and "full" is simply every word equal to `!0`.
- Phase 0 task 6: `AtomicBitmap::release` returns the previous word and leaves the abort on `prev & mask != mask` to the caller in `slab.rs`. Reason: keeps the module pure logic that `cargo test` can drive on the host while still detecting a slot released twice from two caches.
- Phase 0 task 6: claims use `Acquire` and releases `Release`. Reason: POSIX requires `malloc`/`free` to synchronise memory, so a slot's new owner must happen-after its previous owner's writes; jemalloc orders its bitmaps the same way.
- Phase 0 task 6: `TwoLevelBitmap` is exactly two levels as designed, but tracks `l1_used`, the number of leading level-1 words that can be non-zero, and `lowest_set` scans only that prefix. Reason: real universes (2^22 slabs, 2^28 huge pages) need 1024 to 65536 level-1 words, and an unbounded scan would touch and commit every summary page; with the bound a heap of a few thousand slabs does one word plus two `tzcnt`s, matching the design's intent.
- Phase 0 task 6: `TwoLevelBitmap` storage is caller-provided zeroed `u64`s sized by `words_needed`, level 1 first then level 0, accessed through a raw pointer with no lifetime. Reason: task 7 carves it out of the metadata region, which lives for the process; tests back it with a `Vec`.
- Phase 0 task 7: `src/lock.rs` is a new module holding one futex mutex type (`RawLock`, `Lock<T>` with a guard), Drepper's "mutex, take 3": CAS to lock, short spin, then `FUTEX_WAIT`; `FUTEX_WAKE` only when the word says a waiter may sleep; off Linux the wait is a yield so host tests run. Reason: design 9 names class, huge, metadata and background-thread locks but section 17 gives them no home, and `meta.rs` is the first user.
- Phase 0 task 7: the metadata region is carved from both ends. Objects (`Heap`, `ClassCache`, ...) come from a bump pointer at the base, committed ahead in 64 KiB chunks, with freed objects on per-bin free lists; reservations (descriptor arrays, bitmaps, stacks) come downward from the top, page aligned and uncommitted, and the owner calls `Meta::commit` on the pages it starts using. Reason: design 4 wants descriptor arrays committed on demand as the region grows, and committing whole tables up front would charge tens of GiB of overcommit under `vm.overcommit_memory=2`; two watermarks growing towards each other need no free-space tracking.
- Phase 0 task 7: object bins are 16, 32, 48, 64, 128, then 1.5x and 2x steps up to 1 MiB (31 bins); bins below 64 are 16-aligned, all others cache-line aligned, and there is deliberately no 96 bin. Reason: a heap or cache of one thread must never share a cache line with another thread's, so every bin from 64 up is a multiple of 64; consecutive bins differ by at most 2x so internal waste is bounded.
- Phase 0 task 7: `Meta::alloc` returns null on region exhaustion or a failed `mprotect` but aborts on a layout it cannot serve (size above 1 MiB, alignment above 64) and on `free` of a pointer outside `[base, bump)` or misaligned for its bin. Reason: exhaustion is a resource failure that `malloc` must turn into `ENOMEM`; the others are allocator bugs, and design 14 says abort on inconsistency.
- Phase 0 task 7: `Meta::commit` trusts the caller to commit each page once and only sums lengths into `stats.committed`; `mprotect` itself is idempotent. Reason: per-page commit tracking would cost a bitmap over 2^36 bytes of metadata for a counter that is only reported, and every owner already keeps a high-water mark.
- Phase 0 task 7: memory fresh from the bump pointer is guaranteed zero (never touched, kernel zero pages), reused objects are not; `alloc_zeroed` scrubs only when the block came from a free list (address below the old bump). Reason: avoids touching pages for large fresh arrays while keeping a cheap zeroed path for `Heap` creation.
- Phase 0 task 8: a refill reserves its wanted count in the descriptor's `live` under the class lock *before* claiming bits, and gives back the unused part afterwards (`unreserve`). Reason: design 4 and 5 claim outside the lock but purge needs `live == 0` under the lock; without the reservation a purge could `MADV_DONTNEED` a slab whose slots a thread had just claimed, and the calloc `zeroed` flag would be unsound.
- Phase 0 task 8: `ClassState` keeps a third `TwoLevelBitmap`, `purged`, next to `partial` and `empty`. Reason: design 5 selects "the lowest Purged slab" before committing a new one, but the `ClassState` sketch lists only two sets.
- Phase 0 task 8: the `zeroed` flag of a claim is true only for the thread that moved the slab from `Fresh`/`Purged` to `Active` under the lock; a second thread refilling from the same still-untouched slab gets `false`. Reason: state alone cannot tell a concurrent claimer whether a slot was dirtied and released in the window before the transition; the conservative answer only costs a `memset` in `calloc`.
- Phase 0 task 8: a partial bit may be stale (slab actually full). Only a refill that observed the slab full clears it, after re-checking `is_full` under the lock; a releaser sets it when the word it cleared was `!0`. Reason: with lock ordering this guarantees every slab with a clear bit is (or will be) in the partial set, which is all first-fit needs; the cost is one extra lock and scan per newly filled slab.
- Phase 0 task 8: guard slabs are committed read-write like their neighbours and get `MADV_GUARD_INSTALL` on their first page; if the install fails the slab is re-protected `PROT_NONE`. Callers pass `guard_interval = 0` when the kernel lacks guard regions. Reason: a `PROT_NONE` slab every N slabs splits the region into one VMA per guard (plan Phase 2 task 1 forbids that), while a guard region inside a read-write VMA does not.
- Phase 0 task 8: `ClassState` owns the class's descriptor array and commit watermark as well as the per-arena sets. Reason: Phase 0 has one arena; Phase 1 task 3 must split the shared per-class table (descriptors, `next_slab`) from the per-arena `ClassState` when arenas arrive.
- Phase 0 task 8: descriptor arrays and the level-0 words of the three slab sets are committed page by page as `next_slab` grows; level 1 of each set is committed at creation. Reason: with 2^22 slabs per class the descriptor reservations alone are about 13 GiB (`quantum16`), which must stay uncommitted under `vm.overcommit_memory=2`.
- Phase 0 task 8: `ClassState::desc` aborts for a slab number at or beyond an atomic `committed_slabs` mirror of the watermark. Reason: a `free` of a pointer into a never-committed slab would otherwise fault on the `PROT_NONE` descriptor page instead of aborting with a message.
- Phase 0 task 8: `dirty_at` is `max(now_coarse_ns, 1)` so 0 always means "not Empty"; `purge_empty(cutoff)` purges under the class lock with one `madvise` per slab. Reason: the batched `process_madvise` driver and the decay deadlines are Phase 1 task 2; this gives the state machine a reachable `Purged` state now.
- Phase 0 task 9: `heap.rs` defines `Shared` (the `Meta`, the `Regions`, `[ClassState; NCLASSES]` for arena 0, the GC interval and the thread-exit key), initialised in place by `Shared::init`; every `Heap` keeps a back pointer to it. Reason: design 17 gives the process-wide state no home, the class states borrow `meta` and `regions`, and the key destructor receives only the heap pointer. Task 11 puts one `Shared` in a static.
- Phase 0 task 9: a heap's unused cache pointers all point at one shared read-only sentinel `ClassCache` with `len == cap == 0`, so the fast paths test only `len` (alloc) or `len == cap` (free) and never a null. Reason: one branch fewer on both fast paths; every write to a cache is guarded by `len > 0` or `len < cap`, and `gc` skips `cap == 0` explicitly (the host test caught a write to it as `SIGBUS`).
- Phase 0 task 9: refill writes the claimed batch reversed so the lowest address is popped first; flush sorts the oldest `cap / 2` entries with `sort_unstable` before `ClassState::release`. Reason: address-ordered first fit (design 5) and one `fetch_and` per bitmap word instead of one per pointer; the sort is amortised over 128 frees and is the first thing to revisit if `larson` shows it.
- Phase 0 task 9: calloc's zero tracking is a per-cache prefix count `zeroed`: a zero refill sets it to the batch size, every push cuts it to the push index, a flush subtracts what it removed, and a pop is zero iff its index is below it. Reason: design 6.3 asks for a per-batch flag; the prefix keeps the flag exact under pushes above the batch at the cost of one `min` on the free path and none on malloc.
- Phase 0 task 9: cache capacity is the fixed class default (256 up to 128 bytes, halving per doubling, minimum 8) in Phase 0; GC every 64 slow paths on a 10 s interval releases three quarters of each cache's low water (jemalloc's rule) and restarts tracking without shrinking `cap`. Reason: the tunables that would drive adaptive capacities are Phase 1 task 1; low-water tracking costs one `min` on pop.
- Phase 0 task 9: no top-4 cache compare on free. Reason: design 6.3 calls it optional, and Phase 2 task 3 owns the hardening tunables together with the benchmark rows the plan demands for them.
- Phase 0 task 9: after the key destructor the TLS slot holds `TLS_EXITED` and the thread is served straight from the slab bitmaps, as it is while the slot holds `TLS_CREATING`; `pthread_setspecific` failure aborts; `pthread_key_create` failure is remembered (`Shared::has_thread_key`) and leaves exiting threads' heaps unreclaimed. Reason: glibc re-runs destructors for up to four rounds if a later destructor allocates, and creating a heap per round would leak cached slots; jemalloc also aborts when it cannot set its TSD.
- Phase 0 task 9: `free` of a pointer in the huge region aborts with a placeholder message. Reason: the huge allocator is task 10; aborting is the only honest answer until then.
- Phase 0 task 10: the huge region is an extent allocator: every page below the high-water mark `next_page` belongs to exactly one extent (an `Active` run including its guard page, or a free `Empty`/`Purged` extent), adjacent free extents are always coalesced whatever their states (the merge is `Empty` unless both were `Purged`), and pages never handed out count as clean. Reason: first fit over the free-page bitmap then always lands inside one extent, so a split touches at most two descriptors and the calloc zero flag is exact; the cost is that a later purge may `MADV_DONTNEED` clean pages that were merged into a dirty extent.
- Phase 0 task 10: the descriptor table is open addressing with linear probing and backward-shift deletion over 16-byte `(key, desc)` entries at a load of one half or less; a run is keyed by its start page, a free extent by its first and last page. Tables up to 1 MiB come from `Meta::alloc`, bigger ones from `Meta::reserve_committed` and are leaked when outgrown (at most the size of the final table in total). Reason: design 7 names a hash table keyed by start page; the last-page key is what lets `free` find both neighbours in O(1) without a page map, and storing the key per slot is what makes backward-shift deletion possible with two keys per descriptor.
- Phase 0 task 10: `Empty` extents live in a FIFO list ordered by `dirty_at` rather than an address-ordered set; when a free coalesces, the `Empty` participant with the oldest `dirty_at` survives and keeps its list position, so `purge_empty(cutoff)` is a pop from the head. Reason: decay needs age order and the free bitmap already supplies address order; the design's "empty set ordered by address" would make every purge a full scan.
- Phase 0 task 10: with `MADV_GUARD_INSTALL` the guard page is committed read-write like its run and the guard is removed when the run is freed, so free extents never contain guards and runs stay in one VMA; without it the guard page is `PROT_NONE`, and every allocation re-commits its whole usable range with one `mprotect` so stale `PROT_NONE` guards inside a reused extent become writable. Reason: design 7 wants both modes; one idempotent `mprotect` per huge allocation is cheaper than tracking per-page protection.
- Phase 0 task 10: alignment above a page picks the first aligned start inside each free extent (or at the mark); the pages before and after the run stay free extents in the extent's state, and a hole at the mark becomes a `Purged` extent. Reason: design 7 "over-allocate and release the head and tail" without a separate release step.
- Phase 0 task 10: every fallible step of `Huge::alloc` (two descriptor allocations, table growth, bitmap commit, `mprotect`, guard install) runs before any state changes, so a failure returns null and leaves the allocator untouched; `Huge::free` cannot fail, so its table growth is best-effort and a fuller table just probes longer. Reason: `malloc` must turn resource failures into `ENOMEM`, and a half-applied split would be a heap inconsistency.
- Phase 0 task 10: `Shared` gains `huge: Huge` and `Shared::init` a `guard_install` flag; `Heap::free` classifies with `Shared::classify_free` and routes huge pointers to a cold `free_huge`; `Heap::alloc_huge`/`Shared::alloc_huge` bypass the caches. The slab fast path is instruction-for-instruction the same as before (the huge arm was already a cold call), and no benchmark row exists because nothing is exported yet; the first Phase 0 acceptance run is the baseline. Reason: the huge allocator is unusable without a free route, and the plan's benchmark rule cannot be met before task 11 exposes `malloc`.
- Phase 0 task 10: `huge_retain_max` is an `AtomicUsize` on `Huge` (`set_retain_max`) defaulting to 64 MiB, and `Huge::free` returns the usable bytes released. Reason: Phase 1's `malloc_conf` needs to set it without a lock, and the thread counters need the size without a second lookup.
- Phase 0 task 10: `bitmap::TwoLevelBitmap` gained `set_range`/`clear_range`, and `class::Lazy`/`class::Set` became `pub(crate)`. Reason: a 64 MiB run is 16384 bits, and the huge free-page set is exactly the lazily committed set `class.rs` already had.
- Phase 0 task 11: the C-ABI exports live in a `cfg(not(test))` submodule as one-line wrappers over `pub fn` Rust implementations. Reason: `cargo test` links the crate into the test binary, where a `#[no_mangle] malloc` would interpose the binary's own allocator; the Rust functions are unit-tested in-process against the real global state and the exported symbols are tested through the release `.so` under `LD_PRELOAD`.
- Phase 0 task 11: the fork prepare handler takes the class locks in index order, then the huge lock, then the metadata lock. Reason: class and huge code take the metadata lock while holding their own and nothing nests the other way, so this order lets any in-flight operation finish; taking metadata first could deadlock against a thread holding a class lock and waiting for metadata.
- Phase 0 task 11: `pthread_atfork` is registered before `Ready` is published, and an allocation from the initialising thread during init aborts with a message rather than being served. Reason: design 10 says init must not allocate; glibc's first 48 fork handlers come from a static array, so the abort path is a bug detector, not a code path.
- Phase 0 task 11: `guard_slab_interval` is 8 when `MADV_GUARD_INSTALL` probed and 0 otherwise. Reason: `class.rs` requires 0 without guard regions because the `PROT_NONE` fallback would split each class region into one VMA per guard; Phase 2 task 1 owns the tunable.
- Phase 0 task 11: `free`, `realloc` and `malloc_usable_size` of a non-null pointer before init abort without initialising the allocator. Reason: design 10 says such a pointer is invalid, and initialising just to classify it would only delay the same abort.
- Phase 0 task 11: huge `realloc` keeps the pointer only when the new size needs the same number of pages; otherwise it allocates, copies and frees, with no in-place shrink. Reason: design 6.3 describes exactly alloc/copy/free; in-place huge shrink and `xallocx` growth arrive with the jemalloc API in Phase 1.
- Phase 0 task 12: the C drivers live in `src/api/ctests.rs` (`cfg(test)`), one `#[test]` per program, not in `tests/*.rs`. Reason: the crate is only `cdylib`/`staticlib`, so Cargo integration tests cannot link it; and under `api::` they run in the second `make test` process together with the other `LD_PRELOAD` tests.
- Phase 0 task 12: every program calls `require_challoc()` (`malloc_usable_size(malloc(1)) == QUANTUM` and `dlsym("challoc_tls_get")`) and the driver first runs it without the preload and asserts failure. Reason: a broken preload would otherwise let glibc pass the whole suite.
- Phase 0 task 12: the "thread exits with a full cache" criterion is checked as a leak bound: 200 threads each fill and free 300 slots in seven classes, and the number of distinct slot addresses per class must stay at or below 4x300. Reason: a cache that was not reclaimed by the exit destructor would consume fresh slots every round and grow linearly; the bound is what makes the test fail rather than merely run.
- Phase 0 task 12: pointer identity across `realloc` is compared as `uintptr_t` and a block kept after a failed `realloc` is reached through a `volatile` copy. Reason: gcc 15's `-Wuse-after-free` (on under `-Wall`, and `-Werror` is set) rejects even comparing a pointer that was passed to `realloc`.
- Phase 0 task 11: `free_sized` and `free_aligned_sized` ignore their size and alignment arguments. Reason: C23 makes a mismatch undefined and glibc's implementation is plain `free`; checking the size against the class is a Phase 2 hardening option.
- Phase 0 task 11: `TwoLevelBitmap::lowest_set_from` only reads a level-0 word whose level-1 bit is set. Reason: the lazily committed sets in `class.rs` and `huge.rs` leave level 0 `PROT_NONE` beyond the high-water mark; a set level-1 bit means the word was written, so it is committed. The old code read `l0(from / 64)` unconditionally, which the small test regions hid through page rounding and the real 1 TiB huge region (level 1 exactly 512 KiB) exposed as a segfault on the first huge allocation.
- Phase 0 task 11: `Regions::reserve` over-reserves the huge and metadata mappings by `MAX_SLAB` and aligns their bases up before applying the random slide. Reason: `mmap` guarantees page alignment only; on native kernels the top-down placement happened to be aligned, but under Rosetta with concurrent tests it was not, which failed the layout and huge alignment tests and would have left the real allocator with a base the design says is `MAX_SLAB`-aligned.
- Phase 0 task 11: `make test` runs the `api::` tests in a second `cargo test` process. Reason: they initialise the real allocator (53 TiB superblock, 1 TiB huge, 64 GiB metadata reservations) for the life of the process, and the layout tests then reserve a second full layout; native kernels take both, Rosetta traps with "could not find free space" for its own bookkeeping.

- Phase 0 task 13: the fuzz driver includes `tests/c/common.h` (via `-Itests/c`) and is driven by `src/api/ctests.rs` like the task 12 programs, at 400k ops x 4 threads and 200k ops x 1 thread x 64-slot table, so every `make test` runs it; `make fuzz` is the full 10M x 4 run. Reason: one set of CHECK/fill/RNG helpers, and a fuzzer nobody runs finds nothing.
- Phase 0 task 13: blocks are filled and verified over their whole `malloc_usable_size`, not just the requested size, and `realloc` is checked to preserve `min(old usable, new size)`. Reason: overlap between neighbouring slots or a wrong class size shows up only in the tail bytes; the copy length is what `api/libc.rs` documents.
- Phase 0 task 13: sizes include 0 and an 8..16 MiB tier, alignments go up to 64 KiB through `aligned_alloc`/`posix_memalign`/`memalign`, and `realloc(p, 0)` is checked to free and return null. Reason: the task 12 programs cover each of these in isolation; the fuzzer interleaves them with everything else.
- Phase 0 task 13: the seed defaults to a fixed value and `random` draws one from `getrandom`; the seed in use is printed first and a failure prints the exact replay command. Reason: an unattended loop needs reproducible runs, and a failing fuzz run is worthless without its seed.
- Phase 0 task 14: the `no_std` panic handler prints `challoc: <message> [<file>:<line>]` instead of `challoc: panic: panicked at <file>:<line>:\n<message>`. Reason: every heap-inconsistency abort is a `panic!`, and the plan asks for "the challoc message"; the reason should come first and on one line.
- Phase 0 task 14: the double-free negative test has two modes because Phase 0 detects a double free at two different points: `double_free_stale` flushes the thread cache between the two frees (the slot bit is clear, caught by the one-load check on `free`), `double_free_cached` frees back to back (both copies sit in the cache and the batched release catches the duplicate). Reason: a back-to-back double free with the slot still cached is only caught at flush until Phase 2's `double_free_scan`; the test documents that boundary instead of pretending otherwise.
- Phase 0 task 14: `negative.c` routes every bad pointer through a `volatile` and allocates its churn blocks before the victim. Reason: gcc 15 rejects `free` of a stack address, a freed pointer, or an out-of-bounds store as errors under `-Werror`; and a `malloc` after the first `free` would pop the victim straight back out of the thread cache.

Reason: with the natural 512-byte stride and 4 KiB pages every class's hot line lands on the same few L1 sets on Apple silicon; single-threaded alloc-test1 went 2.13 -> 2.52 s and the stall sat on `free`'s epilogue loads. - Phase 0 acceptance (step 1): 128 bytes, not 64, is the padding unit. Reason: Apple silicon has 128-byte lines and Intel's adjacent-line prefetcher pairs 64-byte lines; 128 covers both. `meta::CACHE_LINE` stays 64 (bin geometry) and is a separate question (remediation step 3).
- Phase 0 acceptance (step 1): `Shared` is `repr(C)` with `regions` first, then the class array, then `meta` and `huge`. Reason: `regions` is read by every `malloc`/`free`; the `meta` and `huge` locks must not share its line.
- Phase 0 acceptance: each remediation step gets its own results file `bench/results/<date>-<arch>-<step>.md` run with `ALLOCS="challoc jemalloc"`, not a rerun of the full four-allocator protocol. Reason: two full runs on the same day differed by up to 40% on every allocator (host load), so a step is only judged against jemalloc measured in the same run; the before-row is the previous file.
- Phase 0 acceptance (step 2): a refill takes the class lock once and reserves from up to 8 slabs in that one hold (`ClassState::plan`), reserving at most `nslots - live` from each: `live` is incremented under the lock before any bit is set and decremented only after bits are cleared, so it is an upper bound on set bits and the reservation is always claimable. Reason: the old `select`/`on_full` pair took the lock once per slab visited plus once more per slab it found full, and a producer/consumer pattern (xmalloc-test) visits several nearly full slabs per refill.
- Phase 0 acceptance (step 2): a claim that scans every word of its slab without finding a bit rescans instead of giving back the reservation; only after 2^22 empty passes does it abort. Reason: `claim_from` inspects each word once, so when a concurrent claimer wins the bits it was about to take the scan comes up short although the slots exist (seen in `fork_alloc` and mimalloc stress on the first attempt, which aborted); unbounded contention on one slab that lasts millions of passes is an inconsistency, not a schedule.
- Phase 0 acceptance (step 2): a partial bit is cleared eagerly only when a plan reserves every slot of a slab with `live == 0` (fresh, purged, or empty); a slab with live slots that gets filled keeps a stale bit until the next plan finds it full under the lock. Reason: with nothing allocated in the slab no release can race the clear, while for a live slab a release between the reservation and the claim could leave a free slot in no set.
- Phase 0 acceptance (step 2): `release` collects the slabs whose words went from full to not full and sets their partial bits under one lock hold at the end of the batch (`Reopen`, 8 entries, flushed early on overflow), skipping slabs that are no longer `Active`. Reason: a sorted flush of 128 slots from a consumer thread hit several full words of one slab and took the lock for each; a slab that went `Empty` in the meantime is in the empty set and must not be put back in the partial set.
- Phase 0 acceptance (step 2): `SlabDesc::live` is loaded with `Acquire`. Reason: a releaser clears bits and then subtracts, so a planner that sees the smaller count must also see the cleared bits for `nslots - live` to be a sound lower bound; the load sits under the class lock, so the cost is nil.
- Phase 0 acceptance (step 3): `meta::CACHE_LINE` is 128 (const-asserted equal to `lock::PAD_ALIGN`): bins are 16, 32, 48, 64 at 16-byte alignment, then 128, 256 and the 1.5x/2x ladder from 384 up, all 128-aligned and 128-multiples (30 bins; the 192 bin is gone, `bin_for` promotes an over-aligned small layout to the 128 bin). Reason: a 64-byte-aligned `Heap` (512-byte bin) or `ClassCache` (3072) placed at 64 mod 128 shared a 128-byte line at each end with a neighbouring thread's object; making every object from 128 up a whole number of 128-byte lines removes that without a per-object pad. Cost: a 16-slot cache (144 bytes) now takes 256 instead of 192; nothing else moves bin.
- Phase 0 acceptance (step 4): the exported `malloc` and `free` contain no calls except one tail call each to a cold `malloc_slow`/`free_slow` that redoes the whole operation from scratch (init, heap creation, refill or flush, huge runs, and every abort). Reason: a `bl` into any diverging cold function (`invalid_free`, `never_committed`, `panic_bounds_check`) made LLVM keep a five-register frame with a 12-instruction prologue/epilogue on every call; with only tail calls the entry points are frameless (`free` 78 -> 73 instructions, `malloc` 56 -> 51 including the cold blocks). The slow path repeats the checks, so a fast-path `false` for a bad pointer ends in the same abort message as before.

Reason: the old path checked `class < NCLASSES` three times (once real, twice through `cs.class()` on a `u16`), recomputed `bitmap_words` to bounds-check a slot already known to be below `nslots`, and loaded `class` then the stride table as two dependent loads.

- Phase 1 acceptance step 3 (b), the compacting cache (`docs/design.md` 6.4, review P1): implemented as scheduled address-ordered pops with three departures from the review's sketch, each forced by a VM measurement recorded in `bench/results/2026-09-17-aarch64-gce-compacting-cache.md`. (1) The run of low addresses is *descending* in the slot array (the pre-change reversed refill batch, lowest on top) and the scheduled pop serves `slots[run_end - 1]`, not an ascending run with a cursor: an ascending batch makes ordinary pops descend and xmalloc-test's consumer then pushes descending over an ascending kept half, which takes the flush's `sort_unstable` off its O(n) sorted-input path (-76% on the arm64 VM, the mirror of it11's -41% reverse pathology). The flush is therefore unchanged and drops the run; a rebuild claims a `cap / 4` block from the lowest partial slab and swaps it into the bottom of the stack, no sort. (2) The schedule is gated per cache: probe mode asks the class once per 4096 pops and compacts only while the class has at least 4 slabs' worth and 1/32 of holes (`ClassState::holes`) *and* its claim counter advanced by less than a slab's worth since the previous probe (`ClassState::claimed`; ordinary refills already take the lowest partial slab, and xmalloc-test's producers run 0..8 slabs of transient holes through a 150..455-slab class that way, measured with `bench/probes/binsample.c`). Unconditional at `k = 3` the schedule cost larson -15..-22% and alloc-test +8..+15%; gated, `new` is indistinguishable from `new0` (schedule off) on larson and alloc-test. A rebuild re-checks and drops back to probing. (3) `run_end <= low_water <= len` keeps the run intact without a second fast-path compare (the `low_water` branch clips both), which means a refill now starts `low_water` at the batch length instead of 0: a GC that finds a refilled batch untouched releases three quarters of it (the design's GC semantics; the old zero was a special case, two tests updated). The probe pop also runs `tick`, so a balanced churn on a dense class still gets GC and decay on a thread without a background thread (the churn probe's emptied slabs were otherwise never purged). Default `tcache_compact_shift:3` (`k` is the plan's; the gate, not `k`, is what keeps the dense benchmarks whole); 0 turns the schedule off. Cache header 32 -> 48 bytes.

- Phase 1.5 task 15 (2026-09-18): the handoff's lock order. The taker holds its class lock throughout `plan` and only ever `try_lock`s a donor's class lock; a busy donor is skipped and the fresh group is the fallback. Reason: no thread then blocks while holding a class lock, so there is no order to argue and the fork handlers' nesting (class locks by arena index, commit locks, set tables) is untouched. The first form locked higher-index donors blocking (consistent with that nesting, `try_lock` downward) and was correct, but on `xmalloc`, where every donor is a producer whose lock also serves its consumers' flushes, the takers joined the convoy (Mac fast tier: +6.1% after the tracking rework, against +9.0% before it); releasing the taker's lock to acquire in order was rejected because another thread of the taker's arena could interleave a refill in the middle of `plan`.
- Phase 1.5 task 15 (2026-09-18): idle-group tracking is the arenas' own `empty` and `purged` sets, nothing more. A group is idle when every committed non-guard slab of it is in its owner's `empty` or `purged` set (the rest are uncommitted `Fresh`), and the taker finds one by locking each other arena's state in turn and scanning its two sets group by group (`ClassState::next_idle_group`, at most `MAX_ADOPT_TRIES` = 8 groups per donor) before it takes a fresh group. Reason: the first form (a per-group `Active` count in the table plus a class-wide idle set under the commit lock, maintained in `take` and `on_live_zero`) failed the Mac fast tier on `xmalloc` (+9.0%, median of 3; RSS 120 -> 61 MiB): for the small classes a group is one slab, so every Active/Empty transition took the shared commit lock and did an RMW on a `busy` line that every arena's interleaved groups share. The landed form adds nothing to the transition paths and moves the whole cost to the fresh-commit path, which pays an `mprotect` anyway.
- Phase 1.5 task 15 (2026-09-18): the transfer moves the donor's commit cursor with the group when the group is the donor's current one (`Inner::group_next..group_end`), so the uncommitted `Fresh` slabs become the taker's current group and the donor's window is closed; `stats.committed` moves for the slabs below the cursor, `empty`/`purged` counts with the set bits, `claimed`/`released` not at all (`live == 0`, so no slot is out).
