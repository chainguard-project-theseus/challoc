## Design decisions

- Phase 3 task 3 (coordinator's decision, on the lane's recommendation; recorded for the human to reverse): the compat header ships as a new subpackage `challoc-jemalloc-compat-dev` with `/usr/include/jemalloc/jemalloc.h` and `provides: jemalloc-dev=${{package.full-version}}` (no `provider-priority`). Reason: Ruby's `--with-jemalloc` probes `<jemalloc/jemalloc.h>` and reads `malloc_conf` through it, and `jemalloc-dev` conflicts with the compat library on the link name and the pc file; a header package of `jemalloc-dev`'s file set makes the swap a one-name change in the consumer's build environment. Measured: `apk add jemalloc-dev` while it is installed is a no-op (the name is provided; task 1's refusal is gone), `apk add ruby-3.4` from Wolfi's repository alone still installs Wolfi's jemalloc. Reversible by dropping the `provides:` line (then the two -dev packages conflict on files and apk refuses, as in task 1).
- Phase 3 task 3: the link name `/usr/lib/libjemalloc.so` and `jemalloc.pc` moved from `challoc-jemalloc-compat` (task 1) to the -dev package. Reason: `split/dev`'s convention and Wolfi's own split (`libjemalloc2` = the `.so.2`, `jemalloc-dev` = link, pc, headers), so each compat package mirrors one Wolfi package exactly and `provides:` names the right one; the task 1 tests moved with the files.
- Phase 3 task 3: the header declares no standard entry point (`malloc`, `free`, ..., `malloc_usable_size`) and includes `<stdlib.h>` and `<malloc.h>` instead; the `je_` names are prototypes, not rename macros. Reason: jemalloc's header redeclares them with its own attributes and `JEMALLOC_USABLE_SIZE_CONST` juggling to stay compatible with glibc's `malloc.h`, which Ruby includes into every translation unit through `ruby/missing.h` (C++ extensions included); glibc's declarations are the ones that must win, and both spellings are real exported symbols of the library, so no macro is needed and `<challoc/jemalloc.h>` can be included alongside.
- Phase 3 task 3: `ruby-3.4`'s `dependencies.runtime` names `challoc-jemalloc-compat` explicitly. Reason: melange derives `so:libjemalloc.so.2` from the binaries and apk resolves a bare `so:` name to the package that carries it (`libjemalloc2`) over a provider (task 1 measurement), so without the name an image would run the package on Wolfi's jemalloc while its test ran on challoc.
- Phase 3 task 3: the package test proves the allocator from inside the interpreter through Fiddle (`mallctl("version")`, `challoc_version()`, `malloc` identity, `malloc_stats_print`) rather than with `MALLOC_CONF=stats_print:true`. Reason: challoc does not implement `stats_print` (accepted, inert, `src/config.rs` `INERT_KEYS`), so the prompt's assertion would have relied on the diagnostic for an inert key; that line is kept in a form that also passes once the key is implemented.
- Phase 3 task 3 (coordinator's decision (2), recorded for the human to reverse): design 13.6's "RUNPATH" wording is now "rpath (`DT_RPATH` or `DT_RUNPATH`)" with the finding that Wolfi's binutils 2.47 emits `DT_RPATH` for `-Wl,-rpath`, searched before `LD_LIBRARY_PATH`, which for Valkey's private library is the better of the two. The alternative is `-Wl,--enable-new-dtags` in `valkey-9.1.yaml`.
