## Design decisions

- Phase 3 task 5 (b): the server runs as a non-root OS user (`pgb`) the script creates with busybox `adduser`, started through busybox `su -s /bin/sh pgb -c "env LD_PRELOAD=... pg_ctl start"`. Reason: postgres refuses to run as root and Wolfi's busybox `setpriv` has no `--reuid`; `env LD_PRELOAD` inside the command line sets the environment after the uid change, so the postmaster and every process it forks inherit it (checked in the postmaster's and one backend's `/proc/<pid>/maps`) and nothing setuid is involved.
- Phase 3 task 5 (b): the RSS sampler runs as the postgres user, not as the container's root. Reason: measured on 2026-09-20, root inside the container gets EACCES on another uid's `/proc/<pid>/maps` and `smaps_rollup` (no `CAP_SYS_PTRACE`); the processes' owner can read them, so `su pgb -c 'sh bench/probes/pg-rss-sampler.sh ...'` needs no `--cap-add` in the Makefile.
- Phase 3 task 5 (b): RSS is reported both as the sum of `Pss` (the plan's measure: every shared_buffers page counted once across the postmaster and its backends) and as the sum of `Pss_Anon`, plus the per-backend medians of both. Reason: with `shared_buffers=1GB` the Pss sum is dominated by shared memory identical for every allocator; `Pss_Anon` (heaps and stacks) is where the allocators differ, and a percentage needs both.
- Phase 3 task 5 (b): "final" RSS is the last sampler pass with at least 90% of the run's maximum backend count, and the table shows the passes per run. Reason: a pass over 500 backends' `smaps_rollup` takes tens of seconds on a saturated host (3 passes per 60 s run at 500 backends, about 6 at 100), so the last pass could straddle the backends' exit and count 200-300 of 500; the first render did, and `REPORT_ONLY=1` re-rendered both files from the raw samples (the header says so and keeps the run's commit, date and duration).
- Phase 3 task 5 (b): one data set (`pgbench -i -s 50`, loaded once under glibc) shared by every allocator, one server start per allocator per round, `shared_buffers=1GB`, `synchronous_commit=off`, no checkpoint inside a row, `huge_pages=off`. Reason: the data files do not depend on the server's allocator; the scale-50 set (810 MB) fits shared memory so the select rows are CPU-bound in the backends rather than in read() and the page cache; synchronous_commit=off keeps TPC-B off the hyperdisk's fsync latency; huge pages off so the shared segment is mapped the same on both VMs.
- Phase 3 task 5 (b): p99 comes from `pgbench -l --sampling-rate=0.05` (a 5% sample of the transaction latencies, one log per pgbench thread, sorted after the run and deleted). Reason: pgbench prints no percentile, `-r` gives per-statement averages only, a full log at 300k+ tps is gigabytes over the protocol; a 5% sample is 300k+ latencies per run.

## Notes for the human

- Phase 3 task 5 (b): open item, owner the coordinator with lane A (heap/arena layout): `select500` on aarch64 is 9.4% behind glibc on the median tps (213.1k against 233.1k; jemalloc 229.3k) with overlapping sorted lists; three same-session 30 s A/B pairs gave -5.2%, -6.5% and (order swapped) +2.2%, with equal instructions (162k against 168k per transaction) and L1d/dTLB misses under both, idle 0%: the row is bound by pgbench's 16 threads sharing the 16 CPUs with 500 backends. Re-measure server-bound (fewer pgbench threads, or the client on a second VM) before treating it as a throughput regression. On x86_64 the same row is +3.5%.
- Phase 3 task 5 (b): the `connect20` gap is a property of challoc's per-process layout, not of a code path: a fresh process owns 79 class regions and 251 metadata regions as separate mappings (plus their guards) in a 54 TiB span, and PostgreSQL forks a process per connection. Each connection pays 58 `mprotect` (slab commits), 2.4x the fork time (VMA and anon_vma duplication), 400 more page faults and the teardown of sparse page tables: 5.3 against 3.9 ms of kernel CPU per connection on aarch64, 4.6 against 3.6 on x86_64. Any mitigation (fewer, contiguous reservations per process; lazily created class regions; a cheaper commit than `mprotect`; larger first slabs so a fresh backend touches fewer regions) is lane A/B territory (`src/arena.rs`, `src/class.rs`, `src/layout.rs`) and a design decision (the isolation of size classes in separate ranges with guards is goal 1 of the README); this lane changed nothing under `src/`. The same shape costs 1.7 MiB of Pss_Anon per backend against glibc's 1.2 (+15% of the Pss sum at 500 backends). mimalloc pays the same connect penalty and 9 MiB per backend.
