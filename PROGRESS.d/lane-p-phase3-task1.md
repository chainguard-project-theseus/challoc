## Design decisions

- Phase 3 task 1: the runtime package `challoc` ships only `/usr/lib/libchalloc.so.0`; the `libchalloc.so` link name goes to `challoc-dev` through Wolfi's `split/dev`. Reason: design 13.6 calls the link "for the linker", and every Wolfi library package splits it that way (`jemalloc.yaml`'s `libjemalloc2`/`jemalloc-dev`); the `challoc` test asserts the link is absent from the runtime.
- Phase 3 task 1: `challoc-dev` carries a `challoc.pc` written by the pipeline (the build has none): `Version` is the crate version and `Libs` is `-L${libdir} -Wl,--push-state,--no-as-needed -lchalloc -Wl,--pop-state`. Reason: design 13.6 (a) says a package must link the executable with `--no-as-needed` for the allocator library or the two-level shape silently runs on glibc malloc; putting the scoped flag in the pc file makes `$(pkg-config --libs challoc)` correct by default, and the package test proves it both ways (a program referencing nothing keeps `DT_NEEDED libchalloc.so.0` with the pc flags, loses it with a plain `-lchalloc`). `jemalloc.pc` is left exactly as `scripts/jemalloc-compat.sh` writes it (`-ljemalloc`), since jemalloc consumers such as Ruby already add `--no-as-needed` themselves and the file must match upstream's `jemalloc.pc.in`.
- Phase 3 task 1: `challoc-jemalloc-compat` declares `provides: libjemalloc2=${{package.full-version}}` and no `provider-priority`. Reason (measured in clean containers with both repositories visible): apk prefers the package that carries a name over a provider, so `apk add ruby-3.4` still installs Wolfi's `libjemalloc2` and nothing flips merely because the compat package exists; `apk add challoc-jemalloc-compat` on top purges `libjemalloc2` and Ruby runs on challoc, and naming both together picks the compat library directly, which is how a task 3 consumer swaps (name it in `dependencies.runtime` and in place of `jemalloc-dev` in its environment). A `provider-priority` above `libjemalloc2`'s (none) would switch every jemalloc consumer at once; below it is impossible. `jemalloc-dev` is not provided: the compat package has no header, and apk already refuses to co-install the two (`pc:jemalloc` conflict).
- Phase 3 task 1: the source step is `git-checkout` of `github.com/chainguard-dev/challoc` at `v${{package.version}}`, guarded by a melange build option `local-source` that skips it and builds the `--source-dir` tree. Reason: Wolfi convention needs a tagged upstream, this repository has neither a public remote nor a tag yet, and the option lets the same file be built from a working tree without editing it; `expected-commit` is the `main` commit the file was written against (4a7d30c), to be replaced by the tag's commit in the Wolfi PR. A version-check step fails the build if `Cargo.toml` or `VERSION_STR` moves without the YAML.
- Phase 3 task 1: no `libchalloc.a` in any package. Reason: the Phase 1 task 6 decision (no static compat library until a `-static` link's fork and TLS behaviour is tested) applies to the system package as well; `split/static` is a one-line addition when it is.
- Phase 3 task 1: the compat build runs `scripts/jemalloc-compat.sh` inside the pipeline instead of restating its steps. Reason: the staged file set and `jemalloc.pc` are then byte-for-byte what `make jemalloc-compat` and the `api::ctests::jemalloc_compat_stage` test check, and a change to the script reaches the package without a second edit.
