## Design decisions

- Phase 3 task 2: the private `quantum8` library is built inside `valkey-9.1.yaml`, not shipped as a `challoc-valkey` subpackage of `challoc.yaml` nor as a `challoc-valkey.yaml`. Reason: melange's SCA (`pkg/sca/sca.go`) lists a shared object's soname under `provides:` only when the file is directly in `lib/`, `usr/lib/`, `lib64/`, `usr/lib64/` (plus `ld.so.conf.d` paths), otherwise under `vendored:`, and `removeSelfProvidedDeps` (`pkg/build/package.go`) prunes a package's own `so:` dependency only against its own vendored list; built in the Valkey package, `/usr/lib/valkey/libchalloc.so.0` is `vendored: so:libchalloc.so.0=0`, `valkey-server`'s `DT_NEEDED` dependency is pruned, and `valkey-9.1` neither provides the soname (nothing else can pick the quantum8 build) nor depends on any challoc package; as a separate package, `valkey-9.1` would keep an automatic `so:libchalloc.so.0` dependency that apk satisfies with the system `challoc`, a second unused copy in every Valkey image removable only with `no-depends`. It is also design 13.6's wording ("a private quantum8 build of the same source in its own package, the way it gets jemalloc today") and Wolfi's shape for a library a consumer must carry privately (built in the consumer's pipeline, its source in the SBOM through the `git-checkout`, rebuilt by an epoch bump). Cost: one 8 s `cargo build` and `rust-1.98` in every Valkey stream's environment.
- Phase 3 task 2: the client tools keep their allocator link. Valkey links every binary with `FINAL_LIBS`, so `valkey-cli` and `valkey-benchmark` carry `DT_NEEDED libchalloc.so.0` and the same rpath, and the `-cli`/`-benchmark` subpackages get an automatic `so:libchalloc.so.0` dependency satisfied by the system `challoc` (measured: `apk add valkey-9.1-cli` installs `challoc-0.1.0-r0`); next to `valkey-9.1` the rpath makes them load the private copy (`LD_DEBUG=libs`). Reason: correct for them (no quantum requirement; `valkey-cli --version` runs with the system library preloaded), and the alternatives are worse: `valkey-cli` cannot be built without the allocator its `zmalloc.c` calls (`USE_JEMALLOC` is per tree, not per binary), and a static link from `libchalloc.a` is untested (`contrib/wolfi/README.md`, "Nothing is shipped from libchalloc.a"). The test asserts the two entries on all three binaries; the earlier `! readelf | grep` negation was a no-op under `set -e` and is gone.
- Phase 3 task 2: `-Wl,-rpath,/usr/lib/valkey` produces `DT_RPATH` with Wolfi's binutils 2.47 (no `--enable-new-dtags` default); design 13.6 says "RUNPATH". Kept as the linker gives it, the definition and test accept `RUNPATH|RPATH`. Reason: for a private library `DT_RPATH` is the better semantics (searched before `LD_LIBRARY_PATH`, so an environment pointing at `/usr/lib` cannot swap in the quantum16 build; only `LD_PRELOAD` can, and then the server dies at start instead of running on the wrong class table), and it is one flag (`-Wl,--enable-new-dtags`) if Wolfi wants `RUNPATH`.
- Phase 3 task 2: the package test starts the server on a unix socket (`port 0`, `unixsocket /tmp/valkey.sock`) rather than a TCP port. Reason: the task's "free port" is guaranteed by construction and `valkey-cli -s`/`valkey-benchmark -s` cover everything the test needs; the by-hand checks used TCP 6399 to show the same on a port.
- Phase 3 task 2: the pipeline's check step runs the freshly built `valkey-server` with `LD_LIBRARY_PATH=<destdir>/usr/lib/valkey`. Reason: the rpath does not exist in the build environment, and the loader wants the soname file name (`libchalloc.so.0`, which only the staged copy has; cargo's output is `libchalloc.so`). Two build failures before this was right; both in the results file.

The options stand: (a) `challoc-jemalloc-compat` grows a `-dev` subpackage with `/usr/include/jemalloc/jemalloc.h` (declaring the unprefixed and `je_` API, `JEMALLOC_VERSION*` 5.3.0, the `MALLOCX_*` macros; no `JEMALLOC_MANGLE`), conflicting with `jemalloc-dev` by path so a consumer names one of them, the same alternatives-by-name rule the runtime already follows; or (b) Ruby's environment keeps `jemalloc-dev` for the header and the compat library is what the built `ruby` finds at run time (the link name `libjemalloc.so` would then be jemalloc-dev's, pointing at Wolfi's `libjemalloc.so.2`, replaced at install by the compat package's file with the same soname; `DT_NEEDED libjemalloc.so.2` is satisfied either way, `scripts/check-needed.sh` verifies it). (a) is the honest package; (b) needs nothing new but builds Ruby against jemalloc's header, which for the symbols Ruby uses (`malloc_conf`, `mallctl`) is the same ABI. Lane P's recommendation for task 3 is (a), with `tests/c/jemalloc_link.c` compiled against the new header as its test.
