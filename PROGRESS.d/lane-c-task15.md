## Design decisions

- Phase 2.5 task 15 (lane C): default `slice_ext:auto`, by the plan's rule (within noise or better on both VMs: it is, on `quick`, `quick-perf`, `ab` and the same binary on/off oversubscribed). No benefit was measurable either: the rows the task named have almost no holder preemption (the slow-path hold is a few dozen instructions and the rows run at one thread per vCPU), and no GCE Ubuntu or arm64 kernel passes the probe today, so `auto` changes nothing on the reference VMs or Chainguard OS and only switches on for an x86_64 host whose kernel enables the option. The human decides with the numbers in `bench/results/2026-09-19-x86_64-lane-c-task15-slice-ext.md` section 9; `off` is one key away.
- Phase 2.5 task 15 (lane C): the enable is per task, not per process (the plan said "per process"; `rseq_slice_extension_prctl` sets `current->rseq.slice.state.enabled`, `rseq_fork` resets a `CLONE_VM` child's rseq state and copies it to a plain fork child; confirmed on 7.0.14 by `tests/c/slice_ext.c`: 32 new threads at `prctl(GET) == 0` before their first allocation, 32 at 1 after, the fork child at 1). So init enables only the init thread and every other thread is enabled lazily by `slice::acquired` on its first lock hold, keyed on bit 5 of its own `flags` (the same cache line as `slice_ctrl`, so the check is one load per hold); a `prctl` that fails switches the process off instead of retrying a syscall per hold. Nothing needs re-enabling in a fork child.
- Phase 2.5 task 15 (lane C): `on` follows PercpuArena's `percpu` shape, not `spin_hint`'s `Issue::Unavailable`: a kernel without the option is the documented fallback, not a configuration error, so `on` with a failed probe is not an issue (no stderr line, no `abort_conf` abort), requests nothing (a field the kernel does not read cannot be forced), and is noted in the report line (`; slice_ext:on requested, unavailable`). `opt.slice_ext` reads back `on`.
- Phase 2.5 task 15 (lane C): every `RawLock` gets the request (class, table, huge, metadata, statistics, background), not a chosen subset: they are all slow-path holds and the per-hold cost did not register. Nested holds (the fork handlers, heap creation under the cache-table lock) request per lock and the inner release withdraws the request, so the outer hold goes on unextended; a per-thread depth counter would need TLS the lock module does not have and the loss is only the extension.
- Phase 2.5 task 15 (lane C): where `rseq_slice_yield` returns `ENOSYS` but bit 4 is set (Docker's default seccomp profile hides every syscall newer than its table while letting the `prctl` through; found on the C4 with the custom kernel: `ENOSYS` in the container, 0 with `--security-opt seccomp=unconfined`), the grant is ended with `sched_yield` instead of turning the extension off: any syscall entry inside a grant revokes it and reschedules, and the grant path is rare (17 per 10^9 operations). The report says which syscall is in use. The plan's "use the dedicated one" holds wherever it reaches the kernel.
- Phase 2.5 task 15 (lane C): `slice::acquired_area` (the release's pointer) is keyed on "the probe has passed" rather than "the extension is on", so a hold that stored its request before another thread switched the process off (a failed `prctl`) still withdraws it.
- Phase 2.5 task 15 (lane C): the unit test for the granted path runs a CPU hog per CPU beside the 4x-CPU lock threads: with only futex sleepers as competition a holder alone on its CPU is never preempted (0 grants in 3 s on the custom kernel with `--test-threads=1`; 12 with the rest of the suite running beside it), and the assertion `grants > 0` needs runnable competition to be deterministic.
