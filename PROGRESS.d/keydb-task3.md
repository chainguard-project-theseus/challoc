## Notes for the human

- KeyDB's defrag needs one thing beyond the hint, and it is not the allocator's to give: its stop rule (Redis 6.2's `active - allocated` over the whole allocator, `computeDefragCycles`) against `unit/memefficiency`'s 5% / 2 MB has a floor under challoc of 8-12% on the suite's workloads, attributed by hand in the results file to (1) thread-cached free slots pinning slabs until the 10 s cache GC returns them (up to 6 MB; `MALLOC_CONF=tcache_gc_interval_ms:1000,tcache_nslots_small_max:200` removes the term), (2) 16-slot slabs of the 64-256 KiB classes in arena 0 pinned by live client/query buffers the defragmenter never asks about (about 8 MB; design 13.4's "megabytes on an idle server"), (3) slab tails and two-slab idle classes (about 1 MB per active arena). The defragmenter itself works (1.5-2.0 -> 1.09-1.18 in two seconds; the both-ways preload shows the dependency). At KeyDB's defaults (10% / 100 MB) the cycle stops at once, so a production KeyDB does not spin. Options, none taken here: a KeyDB-side `frag_smallbins` rule (Redis 7 / Valkey), a `memefficiency.tcl` threshold hunk in the package patch (for the record only; the package build does not run the suite), or on challoc's side smaller slabs for the classes above 4 KiB and a faster default cache GC (lane A/B files; a performance question). Carried as an open item.
- `get_defrag_hint` answers for every slab class since 896a60d (kept: the right rule for a slab allocator, no allocation-path cost, tested both ways); on KeyDB's suite it recovered nothing, since the pinning blocks are not the defragmenter's objects. The coordinator may prefer the bin-only rule of 9d62dbb for symmetry with the utilization queries; both are tested.
- Two assertion no-ops in package tests: under `set -e` a `! command` never fails a step (POSIX exempts `!` pipelines), and `apk info -e libjemalloc2` exits 0 because the compat package provides the name. Fixed in the KeyDB and RethinkDB definitions (`if ...; then exit 1; fi`; `apk info -vv | grep '^libjemalloc2-'`); lane P's `ruby-3.4.yaml` (`! apk info -e libjemalloc2`) and `valkey-9.1.yaml` (`! grep -iE 'challoc:|assert|crash' /tmp/valkey.log`) have the same lines, which have never been able to fail; not changed here (their packages would need re-testing to keep their records honest).
- `readelf --dyn-syms ... | grep -q` under melange's `pipefail` is a SIGPIPE race (exit 141; it killed the first KeyDB check step); the new definitions read the whole input. Lane P's Ruby and Valkey definitions have the same pattern and passed by timing.
- The `provides:` question (compat -dev provides `jemalloc-dev`): it did not affect these builds. Both environments name `challoc-jemalloc-compat-dev` directly and never mention `jemalloc-dev`; apko installed it without conflict and no bootstrap dependency pulled `jemalloc-dev`. RethinkDB is the one case where the swap changes the link shape (static `libjemalloc.a` -> dynamic `libjemalloc.so.2`, `--dynamic jemalloc`): a `challoc-jemalloc-compat-dev` without `libjemalloc.a` cannot stand in for `jemalloc-dev` for a consumer that links statically, so the `provides` is a promise the package keeps only for dynamic consumers; worth a note in the Wolfi PR.
- KeyDB's `runtest` cannot run on Wolfi as shipped (Tcl 9 only; `tclsh8.5/8.6` looked up, `package require Tcl 8.5`, `-encoding binary`); the results file has the three spellings. Wolfi's `keydb.yaml` test does not run the suite, so this matters only to whoever wants to.
- `keydb` `provides = cmd:gcc-wrapper`: Wolfi's `make install` moves `/usr/local/bin/*`, and KeyDB's install drops a `gcc-wrapper` there; pre-existing, unchanged.
- Timing: KeyDB 30 s of make, RethinkDB 5-6 min (its `--fetch protoc` builds protobuf 3.19.4 first) on 16 vCPUs. VMs `challoc-keydb-{arm64,amd64}` deleted at the end.
