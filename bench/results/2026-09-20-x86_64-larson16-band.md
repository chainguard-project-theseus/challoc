## 3. Where the scorecard's 3 points are

The scorecard runs 3 rounds of 5 s per allocator and takes the median.
Today's run at a999097 (`.tmp-scorecard-amd64.log`, the same VM, 40
minutes before the counters above): challoc 299.4 / 302.0 / 314.6 M
ops/s, jemalloc 328.3 / 340.1 / 340.8; medians 302.0 and 340.1, the row
reads +12.6%. The counter runs of sections 1 and 2 put the same library
at 308..321 and jemalloc at 331 on the same host an hour later. A
16-thread row on a 16-vCPU guest spreads 5% within one 3-round run on
each side; the row's percentage inherits both spreads, so a 3-round
median moves by several points between runs with no code change, and
the +9.6 -> +12.9 step at 0f5fea8 (one line) is inside that. What the
first batch did change on x86_64 is nothing on this path; what the
second batch changed (+8 instructions, the dispatch) costs no cycles
here.

## 4. Consequences

- Row 2b of the acceptance list holds for x86_64 as it does for
  aarch64: no default-on change of the phase moves a scorecard row by a
  per-operation cost; the larson16 x86_64 band is +10..13% by the 3-round
  scorecard and +6..7% by the per-operation harness on the same host,
  and the difference is the scorecard's own spread on a 16-thread row.
- The trend note: read larson16 x86_64 against a +6..13% band, and only
  a move beyond it, or a `quick-perf` cycles-per-operation move, as a
  regression. A tighter reading of that row needs more rounds
  (`ROUNDS=5` is the `ab` tier's) or a pinned run (`PIN=1`), not a code
  change.
