# `DT_NEEDED` under `--as-needed`, 2026-09-19 (Phase 3 prerequisite (e))

Lane D. `make check-needed` (`tests/as-needed.sh` in the dev image: Wolfi
gcc 16.2.0, binutils 2.47.20260726) on `challoc-lane-d-arm64` (Neoverse
V2) and `challoc-lane-d-amd64` (Xeon 8581C), library a3ddd6d. The two
outputs are identical apart from the `ld-linux` entry, so one is shown;
the consumer section lists what each VM had built (arm64: Valkey and
Ruby; amd64: Ruby). Design 13.6 carries the conclusion; the checker is
`scripts/check-needed.sh <binary> <soname>...` (readelf only, exit 1 when
a soname is missing), wired into `contrib/valkey/build.sh`
(`libchalloc.so.0`) and `contrib/ruby/build.sh` (`libjemalloc.so.2` on
`ruby` and `libruby.so`).

## The truth

1. Wolfi's toolchain links with `--as-needed` by default: the plain link
   of a program that references nothing of the library (`none-default`)
   drops `DT_NEEDED libchalloc.so.0` without any flag.
2. A program that references `malloc` only keeps the entry, with or
   without `-Wl,--as-needed`: `-lchalloc` precedes the implicit `-lc`, so
   `malloc` is resolved by `libchalloc.so` when it is scanned (the
   linker's `-y malloc` trace: "reference to malloc" from the object,
   "definition of malloc" in `/src/target/release/libchalloc.so`), and a
   library that resolved a reference is kept. Every real consumer
   references `malloc`, so a single executable is safe.
3. A program that calls `challoc_version()` keeps it too, trivially.
4. The two-level shape is the failure: an executable that allocates only
   through a shared library which itself needs `libchalloc.so.0`. Under
   `--as-needed` the executable drops its own entry (the library keeps
   its), and at run time the library's `malloc` binds to `libc.so.6`: the
   loader's breadth-first search order lists the executable's direct
   dependencies (`libc.so.6` among them) before the library's
   dependencies, so glibc's `malloc` wins for the whole process, the
   library's own calls included, and nothing fails. With
   `-Wl,--no-as-needed` the same program's `malloc` is `libchalloc.so.0`.
   Ruby is exactly this shape (`ruby` references no allocator symbol,
   `libruby.so` references `malloc_conf` and `malloc_usable_size`) and its
   configure appends `-Wl,--no-as-needed` to LDFLAGS (ruby/ruby#4627), so
   the built `ruby` carries `libjemalloc.so.2` all the same.
5. The loader wants the soname, not the link name: the `--as-needed`
   malloc variant runs with a `libchalloc.so.0` link on
   `LD_LIBRARY_PATH` and fails to load without it.

What a package must do: link executables with `-Wl,--no-as-needed
-lchalloc` (or `-ljemalloc`; `-Wl,--push-state,--no-as-needed -lchalloc
-Wl,--pop-state` scopes it), or make the executable itself reference the
allocator, and run `scripts/check-needed.sh` in the package test on every
installed executable that must run on challoc and on the shared library
that does the allocating.
