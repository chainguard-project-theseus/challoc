## Failures and readings

F1. 64k-arm64, `make test-cgroup`, the 300 s oscillation: `OUTCOME oscillate
alloc=challoc args='300' status=137 verdict=OOM-killed oom_kill=1` after
cycle 54 at about 164 s, `memory.peak 512 MiB`, in all four attempts with
the same shape. Its cycles read `up 480 MiB in 16 ms (rss 496..500, current
497..507 MiB), down to 200 MiB (rss 286..306, current 292..313 MiB)`; the
same program on the 4 KiB cells reads `up 480 MiB in 61..175 ms (rss
492..493, current 493..496 MiB), down to 200 MiB (rss 395..426, current
397..426 MiB)`, `memory.peak 504 MiB`, verdict ok. So at 64 KiB pages the
up phase sits 7..11 MiB higher (every slab, huge run and guard rounded to
64 KiB; the tail of each partially used page is 16x larger) against a
margin that is only 8..16 MiB at 4 KiB, and one swing touches
`memory.max`; the down phase, by contrast, purges to 100 MiB lower than at
4 KiB (coarser but larger purge units) and is not the problem. The churn
tests (400 MiB freed under 512m/256m, RSS under 100 MiB within 2 s) PASS
at 64 KiB, so the policy works; the headroom the oscillation depends on
(design 11, sized for 4 KiB pages) does not. This is an allocator finding,
not a test bug: the fix (a headroom expressed in pages, or a policy that
reacts before the last few MiB at large pages) is next iteration's work
(In progress in PROGRESS.md). The 464 tests (the api group with the C
programs included), the fuzzer and the probe pass at 64 KiB after the test
fixes below, so the allocator itself runs on a 64 KiB kernel.

F2 (fixed this iteration, test bugs). The 64 KiB cell's first attempt had
58 unit-test failures, its second 9, its third 1, its fourth none (464/0, the api
group with the C programs included, the first time it ran on 64 KiB pages): every one a test assuming the 4 KiB page. In order of
discovery: `huge.rs`, `heap.rs`, `purge.rs`, `class.rs`, `meta.rs` and
`stats.rs` test modules had `const PAGE: usize = 4096` (or `let page =
4096`) and built real `PROT_NONE` reservations with it; on a 64 KiB kernel
the class environment's `fake page must be a real page multiple` assertion
fired for every test (56 of the 58), `Meta::new` rejected the unaligned
region, the huge environment's commits were not page aligned. Then the
tests' arithmetic: `held.len() == pages / 257` (a 1 MiB run is 17 pages of
64 KiB, not 257), `Backing::new(1 << 16)` (one page, so a reservation
covers the whole region and "commit outside" cannot happen),
`with_meta_len(3 * page)` as a "too small" metadata region (192 KiB is
enough at 64 KiB), "64 KiB holds exactly 64 objects" (16 pages is 1 MiB
there), the class tests' 8 MiB metadata exhausted by 64 KiB-rounded table
reservations (`works_for_every_class` reserves three per class), the
faked 16 KiB page of the page-group tests (smaller than the real page, so
not reservable; skipped when the real page is larger, which is the case
they simulate). The fixes: a `page_size()` helper per test module (the
kernel's page on Linux, 4 KiB on the host), the huge test region defined as
16384 pages (64 MiB at 4 KiB, 1 GiB at 64 KiB), expectations written in
pages. Nothing in `src/` outside `#[cfg(test)]` changed for this.

F3 (a design-table error, corrected). `process_madvise=no` on 5.10, 6.1 and
6.8 (x86_64 and arm64) even with `--privileged` (k68-amd64: identical line
under privileged), `process_madvise=pidfd_self` on 7.0.0-31-generic
privileged. The design and README said "kernel 5.10 with a pidfd of self";
the syscall exists since 5.10 but accepts `MADV_DONTNEED` only from 6.13
(before that only COLD/PAGEOUT/WILLNEED/COLLAPSE), so the batched purge
path needs 6.13 and the `madvise` loop is the path on every older kernel
(it ran on six cells here). Design 17 and README's table now say so. The
probe already behaves correctly (it tries and records the error).

F4 (fixed, test bug). k61-arm64 first attempt:
`class::tests::purge_never_races_a_claim` panicked with `the purger never
found an empty slab` (333 passed, 1 failed; 4 vCPUs, 4 test threads plus
the purger thread; the whole 20 000-iteration main loop is about 4 ms, one
scheduler slice, so the purger was never on a CPU while a slab was empty).
The test now runs past 20 000 iterations until the purger has purged once
(bounded by 30 s); the assertion is about the protocol, not the scheduler.
Passed on every later cell including the same machine type.

F5 (harness, fixed in the driver, no allocator content). Debian's
`core_pattern` is `core` in the cwd: the aborting negative tests left a
root-owned `core` in the bind-mounted tree and every later `docker build`
failed on its context ("no permission to read from .../core"; k61-arm64
and k61-amd64 first attempts, `tests=0/0`); provisioning now sets
`kernel.core_pattern=|/bin/false` as one key (a `sysctl --system` re-applied
GCE's `net.ipv4.ip_forward = 0` and cut every container off apk.cgr.dev,
run2's `tests=0/0`). Ubuntu's generic kernels panicked at boot (`Unable to
mount root fs`) because the GCE image boots initrd-less
(`GRUB_FORCE_PARTUUID`), which only the gcp kernel with built-in storage
drivers survives; the prep clears it and checks the initrd line. Ubuntu's
`grub.cfg` is root-only (`sudo grep`). ssh answers for a while after
`reboot`, so the prep waits for a new `boot_id`. GCE recycles a deleted
VM's external IP within minutes, so matrix ssh keeps no host keys. The
cell's EXIT trap referenced a `local` of a returned function (VM not
deleted; fixed, and the driver's exit trap sweeps the prefix). bullseye's
LTS ended 2026-08-31: its security pool is gone and `git` is not
installable (perl mismatch), so provisioning drops that suite and treats
`git` as optional on the host.
