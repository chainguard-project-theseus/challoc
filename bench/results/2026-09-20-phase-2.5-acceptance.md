### 1.3 gcp-amd64, run 1: `rseq::tests::probe_reads_the_registered_area`

The first run of the gcp-amd64 cell (c3-standard-4, 4 vCPU, Xeon 8481C,
7.0.0-1011-gcp, `rseq=yes rseq_size=33 mm_cid=yes`) failed one unit test
(`matrix/2026-09-20-lane-d-gcp-amd64-run1.log`, line 666):

```
thread 'rseq::tests::probe_reads_the_registered_area' (897) panicked at src/rseq.rs:1409:17:
several running threads share one mm_cid
```

The assertion (`src/rseq.rs` 1385..1409): spawn as many threads as
possible CPUs (4 here), spin 50 ms each reading `mm_cid`, and require more
than one distinct value over the threads. `cargo test` runs the unit tests
in parallel, and at that moment the model checker's per-CPU scenarios
were running beside it (`163125 states in 6.71 s`, `241740 states in
8.22 s` on the lines just above the failure), so on a 4-vCPU host the four
spinning threads can be scheduled one at a time and every one of them
reads the same concurrency id: `mm_cid` is the id of a *running* thread,
and a serialised set of threads legitimately shares one. The cargo
process's `make test` stopped there, so the api:: suite and the cgroup
tests of the target did not run in that pass (fuzz and `make test-cgroup`
did, both PASS). The same test passed on the 16-vCPU lane VMs (under the
key and without), on gcp-arm64, k68-arm64, 64k-arm64 (4 vCPU, `mm_cid=yes`)
and the two c3 cells k68-amd64 and hwe-amd64 (4 vCPU) today, so it is a
load-shaped assertion on a small host, not a probe fault; the cell was
re-run (the table's "run 2"). Owner: lane A (`src/rseq.rs` tests): pin
the spinners or accept one id when the threads did not overlap (compare
against `sched_getcpu` coverage), or run that test with
`--test-threads=1`.

### 1b.2 The three reds, read

Two unit tests, both new since 0c60b1a with lane B's 7ab6916 (task 11, the
prefault pass and the `populate_write` probe), fail the same way on every
run of their cells, so they are not flakes:

- (a) `purge::tests::prefault_populate_and_wakes_are_counted` (src/purge.rs:1504,
  `assertion left == right failed`), k510-amd64 2/2 and 64k-arm64 2/2. The
  test sets `let page = 4096`, aligns a stack buffer to 4 KiB, calls
  `prefault::reset_for_test(true, true)` (the pass on, `populate_write`
  on, whatever the probe said) and asserts
  `(bytes, fallbacks) == (2 * page, 0)` after `populate(addr, 2 * page,
  page)`. `populate` does `madvise(MADV_POPULATE_WRITE)` when the flag is
  on and counts a fallback when the call fails: on 5.10 the advice does not
  exist (5.14) and at 64 KiB pages a 4 KiB-aligned address is not
  page-aligned, so `fallbacks` reads 1 on both. The library configures the
  flag from the probe (`populate_write=no` on 5.10) and populates slabs,
  which are page-aligned, so the reading is a test that ignores the probe
  and the page size; lane B confirms and fixes (`sys::page_size()` for the
  buffer, `reset_for_test(true, probe)` or the fallback count expected where
  the advice cannot work). The 6.1 cells pass because `populate_write=yes`
  there and the page is 4 KiB.
- (b) `sys::features::linux_tests::probe_prints_and_matches_kernel_version`
  (src/sys/features.rs:1714, `fresh scratch page resident before the
  populate`, `left: 1 right: 0`), hwe-amd64 privileged 2/2, and reproduced
  by hand under `DOCKER_FLAGS=--privileged` on both lane VMs at
  7.0.0-1011-gcp (the C4 and the C4A, the single test; the lines are in
  this file's section "At a999097"). The test's `populate_write` block
  asserts, through `mincore`, that its scratch page is not resident before
  `MADV_POPULATE_WRITE`; the `process_madvise` block just above it wrote
  `7` to the same page, `MADV_DONTNEED`ed it through `process_madvise`,
  wrote `9` and `MADV_FREE`d it, and a lazily freed page stays resident
  until reclaim. That block runs only where `process_madvise` works, which
  under Docker is the privileged container (`pidfd_self`; unprivileged,
  seccomp filters the syscall, `process_madvise=no`, the page is untouched
  and the test passes: every unprivileged cell and the reference VMs).
  Lane B: a second scratch page for the `populate_write` block, or
  `MADV_DONTNEED` before the `mincore`. The morning's hwe privileged run
  (540/0 at 0c60b1a) predates the block.
- (c) `heap::linux_tests::percpu_sections_abort_and_retry_under_signals`
  (src/heap.rs:7113, `no section was aborted under 23636 signals`),
  k68-amd64 1 of 3 runs (its privileged run in the same cell and the
