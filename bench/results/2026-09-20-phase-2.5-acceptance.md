### 1.3 gcp-amd64, run 1: `rseq::tests::probe_reads_the_registered_area`

The first run of the gcp-amd64 cell (c3-standard-4, 4 vCPU, Xeon 8481C,
7.0.0-1011-gcp, `rseq=yes rseq_size=33 mm_cid=yes`) failed one unit test
(`matrix/2026-09-20-lane-d-gcp-amd64-run1.log`, line 666):

```
thread 'rseq::tests::probe_reads_the_registered_area' (897) panicked at src/rseq.rs:1409:17:
several running threads share one mm_cid
```

The assertion (`src/rseq.rs` 1385..1409): spawn as many threads as
possible CPUs (4 here), spin 50 ms each reading `mm_cid`, and require more
than one distinct value over the threads. `cargo test` runs the unit tests
in parallel, and at that moment the model checker's per-CPU scenarios
were running beside it (`163125 states in 6.71 s`, `241740 states in
8.22 s` on the lines just above the failure), so on a 4-vCPU host the four
spinning threads can be scheduled one at a time and every one of them
reads the same concurrency id: `mm_cid` is the id of a *running* thread,
and a serialised set of threads legitimately shares one. The cargo
process's `make test` stopped there, so the api:: suite and the cgroup
tests of the target did not run in that pass (fuzz and `make test-cgroup`
did, both PASS). The same test passed on the 16-vCPU lane VMs (under the
key and without), on gcp-arm64, k68-arm64, 64k-arm64 (4 vCPU, `mm_cid=yes`)
and the two c3 cells k68-amd64 and hwe-amd64 (4 vCPU) today, so it is a
load-shaped assertion on a small host, not a probe fault; the cell was
re-run (the table's "run 2"). Owner: lane A (`src/rseq.rs` tests): pin
the spinners or accept one id when the threads did not overlap (compare
against `sched_getcpu` coverage), or run that test with
`--test-threads=1`.
