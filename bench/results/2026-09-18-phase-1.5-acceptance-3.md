arena and class can reuse; the design question this raises is in PROGRESS.md

### 3.1 Why the curve did not move mstress, and what the row actually is

mstress (`mstress 16 50 25`, mimalloc-bench) on the C4 VM, one run per line,
`bench/rt` wall / user / sys seconds and max RSS, with the `arenasample`
probe's exit sample where noted (`~/logs/mstress-it28.log`,
`~/logs/mstress2-it28.log`; the probe filters hid its per-second lines, the
exit lines suffice here):

| library | `MALLOC_CONF` | wall s | user s | max RSS MiB | exit: smaps classes / meta / huge MiB | exit: small dirty / large dirty (nominal) / retained MiB |
|---|---|---:|---:|---:|---|---|
| challoc 2c8731f | default (`dirty_decay_ms:10000`, 17 arenas) | 0.63, 0.63, 0.65 | 4.9 | 351, 340, 341 | 172 / 10.7 / 156 | 41.8 / 301 / 0 |
| challoc | `dirty_decay_ms:1000` | 0.64, 0.63 | 4.9 | 337, 337 | | |
| challoc | `dirty_decay_ms:-1` | 0.63, 0.63 | 4.9 | 343, 342 | | |
| challoc | `dirty_decay_ms:0` | 1.12, 1.13, 1.12 | 4.5 | 262, 262, 260 | 38 / 10.7 / 0.6 | 3.2 / 171 / 41.5 (+125 large) |
| challoc | `narenas:1` | 0.62 | 4.7 | 283 | 124 / 1.2 / 155 | 23.9 / 252 / 0 |
| challoc | `narenas:1,dirty_decay_ms:0` | 1.03 | 4.4 | 242 | 35 / 1.2 / 0.6 | |
| challoc | `dirty_decay_ms:0,tcache_max:262144` | 1.15 | 4.4 | 275 | 61 / 10.8 / 3.0 | |
| jemalloc 5.3.1 | default | 1.05 | 4.9 | 286 | resident 36 at exit (`stats_print`), retained 788 | merged dirty pages 5792 |
| jemalloc | `dirty_decay_ms:-1` | 1.06 | 5.0 | 284 | | |
| jemalloc | `dirty_decay_ms:0` | 1.52 | 5.4 | 259 | | |

("large" in the probe is the classes above `tcache_max`; its dirty figure is
slab bytes, most of them never touched, so it exceeds the class regions'
RSS.) Reading:

- The run is 0.63 s wall. The window settings 1 s, 10 s and never give the
  same RSS (337..351), so nothing in this row ages far enough into any
  window to be purged before exit; the curve (about 6% of the way into the
  default window at exit, weight 0.99) cannot act. jemalloc is the same:
  284..286 with decay on or off. Iteration 27's "+29 MiB of Empty slabs
  waiting out the flat window" was wrong; its probe numbers were right, the
  reading of the run time was not.
- `dirty_decay_ms:0` (purge on the transition to `Empty`) is the only
  setting that lowers the peak, to 262 (below jemalloc's 286), at the price
  of the refaults: wall 0.63 -> 1.12 s, which is still within 10% of
  jemalloc's 1.05 s on this row, but a purge-on-free policy is not one the
  other rows would survive.
- `narenas:1` is 283, equal to jemalloc's 286. The whole gap of the default
  (+60 MiB) is therefore the arena count times what an arena keeps per
  class and cannot lend to another arena or another class: `Empty` small
  slabs 41.8 vs 23.9 MiB (+18), partial small slabs 19.1 vs 10.1 (+9),
  touched pages of `Empty` large-class slabs (classes RSS minus the small
  terms: about 111 vs 90, +21), metadata 10.7 vs 1.2 (+9.5). The huge region
  is the same at 1 and 17 arenas (155..156 MiB). jemalloc with the same 16
  threads and 16 arenas keeps one dirty extent pool per arena that any bin's
  next slab or any large allocation reuses, so its per-arena cost is the
  peak of one pool, not the sum over classes of each class's peak; challoc's
  per-class regions (design section 3) make an `Empty` slab reusable only by
  its own class, and design 13.3 only by its own arena.

The candidates are design changes and are listed for the human in
PROGRESS.md: an `Empty`-slab handoff between arenas of the same class on
the commit path (an arena about to commit a fresh slab takes another arena's
`Empty` slab of that class instead; attacks the +18 and +21 terms, keeps the
partitioning on the hot paths), a per-arena dirty budget (jemalloc 4's
`lg_dirty_mult`, purging beyond it at once, costing refaults), or reading
the x86_64 mstress row as the per-class-region design's price.
