## Reading

- Criterion (docs/plan.md Phase 3 task 5: a row more than 10% behind the
  best of glibc and jemalloc on time or RSS is attributed): no row is.
  Startup is +9.1% against glibc (0.024 against 0.022 s, a 2 ms constant on
  a 22 ms process) and +4.3% against jemalloc, with the smallest max RSS of
  the six (39.1 MiB; glibc 67.1, jemalloc 42.0). The server row is within
  1% of glibc on peak RSS (+0.2%), VmHWM (-0.8%), req/s (+0.8% / +0.3%) and
  CPU per request (+0.7%), and ahead of jemalloc on every one of them (peak
  RSS -13.8%, VmHWM -16.6%, req/s -4.5% / -2.6%, CPU per request -1.7%).
  The six allocators sit within +-3% of each other on req/s and +-3.5% on
  CPU per request; tcmalloc and mimalloc bracket glibc by about 1%, which is
  the run's noise band. p99 is 2 ms for every variant but glibc-arena2 (4 ms).
- Against the sixth variant, glibc with `MALLOC_ARENA_MAX=2` (the fleet's
  usual mitigation): startup +14.3% (3 ms; its list holds a 0.015 outlier,
  the other four runs are 0.021..0.022), peak RSS +5.9% (845 against 798
  MiB), VmHWM +5.2%; challoc serves 2.6% / 0.8% more requests, at p99 2 ms
  against 4 ms and 6.1% less CPU per request: two arenas shared by 200
  threads pay for their lower footprint in arena-lock contention.
- Startup attribution (`sudo perf stat -e page-faults,minor-faults,
  major-faults,task-clock,cycles,instructions,context-switches --inherit -p
  <container init pid>` on the VM host around `sleep 1; exec env
  LD_PRELOAD=... java -version` in the dev container, three runs each, the
  driver's `perf-stat` recipe): challoc 6262 / 6257 / 4054 minor faults,
  129.9 / 128.6 / 107.7 M instructions, 31.1 / 31.3 / 25.8 ms task-clock;
  glibc 4993 / 4995 / 4994 faults, 118.0 / 117.9 / 116.7 M instructions,
  28.3 / 28.2 / 28.1 ms; jemalloc 6417 / 6415 / 6407 faults, 128.0 / 126.8
  / 127.3 M instructions, 30.0 / 30.2 / 30.3 ms. The 2 ms is about 1270
  more first-touch page faults (5 MiB) and about 11 M more instructions:
  challoc gives every size class its own region and every thread its own
  heap in the metadata region, so the JVM's 15 startup threads
  (`-Xlog:os+thread`) each fault fresh slab pages for the classes they
  touch and a fresh heap page, where glibc serves the same requests from
  the already-touched brk heap and a few per-thread arenas; jemalloc's
  isolated-run design pays the same count (6415 faults, +9 M
  instructions). A `/bin/true`-sized process shows no difference at
  `rt`'s 1 ms resolution (200 runs each: glibc 1.00 ms, challoc 1.00 ms,
  jemalloc 2.00 ms), so this is not a fixed init cost but the per-class,
  per-thread first touch, the same 1..2 ms the Ruby startup row found
  (`2026-09-17-aarch64-ruby.md`). One challoc run did less work than glibc
  (4054 faults, 25.8 ms): the JVM's own startup work varies between runs.
  Not above the band; no action.
- Startup RSS: glibc's 67.1 MiB is the per-thread arenas (15 threads; with
  `MALLOC_ARENA_MAX=2` the same process is 41.3 MiB); on the x86_64 VM the
  same glibc is 39.4 MiB (`2026-09-20-x86_64-jvm.md`), so the aarch64
  figure is Wolfi's aarch64 glibc arena geometry, not the JVM. challoc's
  39.1 MiB is the smallest of the six on this architecture.
- Server RSS: idle is 580..602 MiB for every allocator (the pre-touched
  512 MiB Java heap plus the JVM's own mappings), the load adds native
  memory: +264 MiB at peak under challoc, +241 glibc, +220 glibc-arena2,
  +396 jemalloc, +456 mimalloc, +257 tcmalloc; sampled Rss is flat over
  the 300 s under every allocator (challoc 828..832 MiB at every 30 s,
  glibc 835..858), so nothing grows under the churn. At the final sample
  challoc's named regions hold 223 MiB (`challoc:classes` 187.9,
  `challoc:meta` 21.1, `challoc:huge` 13.8) against glibc's 237 (`[heap]`
  11.6 plus 225 of unnamed arenas), glibc-arena2's 211, jemalloc's 310,
  tcmalloc's 248 (`[heap]` 245.7) and mimalloc's 396 (named `mimalloc`).
  challoc's `malloc_stats_print` at exit (bench/probes/statsdump.so):
  allocated 97.9 MB, active 189.6 MB, metadata 25.8 MB, resident 223.6 MB,
  mapped 475.3 MB, retained 251.6 MB, 64 arenas: the 64 KiB direct
  buffers are freed in bursts by the JVM's Cleaner thread after each GC,
  so at any instant about half of the slots in the touched slabs of that
  class are free and waiting for decay (active/allocated 1.94), which is
  the +24 MiB over glibc-arena2 at peak and the -136 MiB under jemalloc.
  Wolfi's aarch64 jemalloc is the 64 KiB-page build (`Page size: 65536`
  in its stats: allocated 112.5 MB, active 308.5 MB, resident 491.3 MB,
  retained 376.8 MB), which is where its 980 MiB peak comes from.
- Throughput: the two generators ran at 63% / 79% of a core (json / blob),
  the server at 7.3 cores of 16 (2188 CPU s over 300 s), so neither side
  was saturated and the closed loop of 32 connections per endpoint set the
  rate. GC count is proportional to requests (10285 challoc, 10296 glibc,
  9956 jemalloc, 10464 tcmalloc): every allocator did the same GC work
  per request. With CPU per request within 1% of glibc and every variant
  within 3% on req/s, the allocator is not on this server's critical
  path; the rows separate the allocators by footprint, not speed.
- The 5-minute rows ran in full (300 s of measured load per allocator
  after 15 s of warm-up; 2052 s for the whole file). The load average at
  the end (7.2) is the server's busy cores plus the two generators; the VM
  was idle at the start (0.00).
